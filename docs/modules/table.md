# 表格的加载状态（shared/table）

对应目录：`apps/web/src/shared/table/`；样式在 `apps/web/src/app/styles/element-theme.scss` 的表格部分。

## 三种情况

列表页按"表格里正在显示什么"决定怎么提示加载：

| 情况 | 例子 | 界面 | 判断（Vue Query） |
|---|---|---|---|
| 没有可显示的数据，正在请求 | 首次进入、切到没看过的分类、加载失败后重试 | 骨架屏 `TableSkeleton`，用 `useDelayedFlag` 延迟显示 | `isLoading` |
| 显示着旧数据，正在等新数据 | 翻页、换条件查询（上一次的数据作为占位）；条件没变时点"查询" | 遮罩 `v-loading`，用 `useDelayedFlag` 延迟显示 | `isPlaceholderData`，或主动刷新中 |
| 显示的就是当前条件的缓存，后台重新请求 | 切回看过的分类、重置回看过的条件、删除后刷新列表 | 不提示，新数据到了直接替换 | 其余的 `isFetching` |

为什么这样分：第一版的遮罩跟着 `isFetching` 走，缓存的数据已经正确显示了，后台重新请求时仍然盖上遮罩，慢网络下看起来是"数据 → 加载 → 又是同样的数据"（3.3 验收时发现，用 2 秒延迟复现）。遮罩的意思是"这些数据已经过时，新的马上到"，只有显示的确实是旧数据时才需要。

- 骨架屏也延迟 300ms 显示：第一版立即显示，请求很快时骨架一闪而过（3.3 验收时反馈）。延迟之内表体留空，不显示"暂无数据"；骨架出现后，数据到了在原位替换，行高相同，不跳动
- `useDelayedFlag` 的"至少显示 400ms"对骨架只在结果为空时起作用（避免骨架一闪就变成"暂无数据"）：有数据时表格不再渲染空状态，数据行立即替换骨架。数据恰好在 300ms 多一点到达时骨架仍会短暂出现，要完全避免就得推迟显示数据，不划算
- 遮罩延迟 300ms 显示（`useDelayedFlag` 的默认值）：内网请求通常更快，快的时候不出遮罩。慢网络下会看到"旧数据 → 0.3 秒后出遮罩 → 新数据"，这是保留旧数据的代价，换来表格不会先变空再撑开
- 条件没变时点"查询"：查询键没变，Vue Query 不会重新请求；用户点查询是想看最新的数据，所以主动 `refetch`，按"显示着旧数据"处理（出遮罩）
- 连续点击：Vue Query 会取消前一次请求，但前一次 `refetch` 返回的 Promise 要等最新的请求完成才结束，所以"主动刷新中"用一个布尔值就够了。这是 Vue Query 的行为，有测试覆盖，升级时留意

写法见 `features/file-management/composables/useFileList.ts`（`initialLoading`、`refreshing`、`refresh`）和 `components/FileTable.tsx`。

## 分页器的总数与页码修正

`ElPagination` 收到的总数小于当前页需要的数量时，会自己把当前页改小，页面随之请求那一页。所以要分清两种数据：本次请求成功返回的结果，和缓存里的旧数据（请求还没结束时先显示的缓存、请求失败后 Vue Query 保留的旧数据）。修正页码只用前者；交给分页器的总数优先用前者，本组条件还没有成功过时先用缓存初始化：

| 情况 | 如果直接用当前显示的数据 | 现在 |
|---|---|---|
| 翻页请求失败 | 没有数据，总数当作 0，跳回第 1 页（请求的页码 1、2、1） | 用本组条件已知的总数，停在当前页，显示"加载失败" |
| 跳回之前缓存过的页 | 先显示旧缓存，它的总页数可能已经过时（例如总数减少时缓存的第 3 页记着"共 2 页"），页码被改小；后台请求返回最新结果时已经离开了这一页 | 旧缓存照常显示，但不用来修正页码；分页器的总数仍用已知的值；请求成功后再按最新结果判断是否越界 |
| 跳回缓存过的页，这次请求失败 | 请求失败后 Vue Query 保留旧缓存，请求也已经结束，看起来和"请求成功"一样，旧的总页数把页码改小 | 失败后保留的旧缓存同样不用来修正页码，停在当前页 |
| 从缓存重新进入列表，后台刷新还没结束就翻页，翻页请求失败 | 本组条件还没有成功过的请求，没有已知的总数；翻页后失败，连缓存也没有，总数当作 0，跳回第 1 页 | 缓存一显示就用它初始化本组条件的总数，翻页失败时停在当前页 |
| 后端返回的页码越界（例如删掉了最后一页的最后一条） | — | 请求成功、拿到的总页数小于当前页时改到最后一页 |

写法见 `useFileList.ts`：

- "一组条件"是页码以外的参数（分类、筛选、每页条数），序列化成键（`hashKey`，忽略值为 `undefined` 的页码），以后新增的筛选条件会自动算进去；`knownTotals` 按这个键记录总数，不需要在条件变化时清空
- 占位数据（`isPlaceholderData`）属于上一组条件，什么都不做
- 本次请求成功：`isFetching` 为 false 且 `isSuccess` 为 true，更新 `knownTotals` 并修正页码。只看 `isFetching` 不够：请求失败后 `data` 仍是旧缓存，`isFetching` 同样是 false，只有状态变成了 `error`
- 其他时候显示的都是缓存，只在 `knownTotals` 里还没有本组条件时用它初始化，不修正页码
- 同时监听 `data`、`isPlaceholderData`、`isFetching`、`isSuccess`，并且 `immediate`（重新进入列表时缓存在挂载时就有）：请求返回的数据和缓存相同时，Vue Query 复用原来的对象（结构共享），`data` 不变，只有请求状态变化
- 分页器的总数：优先用 `knownTotals` 里本组条件的值；换条件时先显示上一组条件的数据占位，总数也暂用它的；都没有时为 0

演变：第一版直接用当前数据的总数，翻页失败会跳回第 1 页；第二版只记一个值、换了条件就清空，"离开后重新进入"和"条件不变再点查询"两种情况记不回来（请求的页码 1、1、3、1）；第三版按条件记录，但仍会被旧缓存的总页数修正页码（总数先减少、再增加后，第 3 页被跳回第 2 页）；第四版只认请求结束时的数据，但请求失败后保留的旧缓存也是"请求结束时的数据"，而且重新进入列表时要等后台刷新成功才有总数，这两种情况下翻页失败仍会改页码。以上情况都有页面测试。

## TableSkeleton

```tsx
import { ElTable, vLoading } from 'element-plus';
import { TableSkeleton } from '@/shared/table/TableSkeleton';

// TSX 中的指令按名字查找，要在组件里局部注册：directives: { loading: vLoading }
const showSkeleton = useDelayedFlag(() => props.initialLoading);
const showMask = useDelayedFlag(() => props.refreshing);

<ElTable data={props.files} height="100%" v-loading={showMask.value}>
  {{
    default: () => [/* 各列 */],
    empty: () => {
      if (showSkeleton.value) {
        return <TableSkeleton />;
      }
      // 骨架屏出现之前表体留空
      if (props.initialLoading) {
        return '';
      }
      if (props.error) {
        return /* 加载失败 + 重试 */;
      }
      return '暂无数据';
    }
  }}
</ElTable>
```

- 放在 `empty` 插槽里：表头和分页不动，只有表体显示骨架
- 20 行，每行高 48，与默认尺寸的纯文字数据行相同（含 1px 分隔线；带 `ElTag` 的行约 49）；铺满表体后多出的行被裁掉
- 每行的骨架条铺满整行（左右留 12，与单元格文字的内边距相同），与表格内容区同宽；没有参数。第一版按 100%、92%、96%、88% 循环长短，看起来没有铺满，3.3 验收时改为统一铺满
- 样式在 `element-theme.scss`：Element 的空状态区域默认只占一半宽度、行高 60，用 `.el-table__empty-text:has(> .table-skeleton)` 撑开；骨架的行高和表格的行高规则写在一起，改一处时同步改另一处

不采用的做法：

| 做法 | 问题 |
|---|---|
| 把整个表格换成 `ElSkeleton` | 表头消失，数据到了表头再出现，界面跳动 |
| 用假数据行渲染真实的列，每个单元格显示骨架条 | 骨架能和列对齐，但每个自定义插槽都要处理假数据，行的类型也要放宽 |
| 每行按列分成几段骨架条 | 拿不到列宽，分段和表头对不齐，反而显得乱 |
