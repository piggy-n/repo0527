## 第一轮上传原型（2026-10-21，已按用户调整确认）

设计理由：以现有文件列表为上下文，复用 FileCategoryTree、FileFilterBar、MxSplitLayout、MxPanel、MxSection 与 Element 组件。元数据和文件分区，整批共用元数据与进度，不引入逐文件独立上传任务。相较重写一份静态样式，这样能直接检查已验收组件的实际排版与键盘交互。

- 源码：`apps/web/src/pages/dev/file-management/`，开发路由 `/dev/file-management`；只在 `devRoutes` 注册，生产构建不包含原型。确认后将弹窗与草稿规则迁到 feature 的 `FileUploadDialog`、`useFileUploadForm`，原型复用正式组件，仅模拟请求结果
- 离线设计稿：当前 worktree 的 `apps/web/public/design.local/file-upload-preview.html`，直接在浏览器打开即可，字体和脚本已内嵌；该目录按规范不入库，不进入生产产物
- 本地生成脚本：`apps/web/design.local/export-preview.mjs`，从 `apps/web` 运行 `node design.local/export-preview.mjs`。临时脚本与截图不入库；持久的可维护来源是上述开发组件，关闭规则由 feature 与原型的测试维护
- 原型只使用固定数据、真实 File 选择对象与模拟进度，不读取文件内容、不发上传/下载请求、不保存偏好。分类切换展示实际分类控件，但固定样例不按后台分类过滤；列表没有复制业务删除操作。下载、查看下一轮补充，不能将本轮当作完整文件管理验收

### 操作与状态

1. 点“上传文档”：默认当前叶子分类，可改选；年份默认今年、禁止未来年份；业务标签必填，备注可选。按用户确认不展示、不提交上传人，现有列表上传人列保留
2. 多选、拖入和逐项移除；未凭空增加文件类型、数量或大小上限；长名称完整换行
3. 点“开始上传”检查空文件和必填项。发送中锁定表单、选择和重复提交；总量未知时不显示假百分比；100% 后进入“文件已发送，正在处理”
4. 用户调整：标题用 `MxTitle level="panel"` 显示蓝色竖条；关闭按钮、右上角 X 或 Esc 清空本次文件和填写，不展示保留草稿的提示。点击遮罩不关闭；已发送的批次用独立快照完成，再打开只查看进度，不能恢复已丢弃的草稿。关闭、组件卸载或路由离开不自动取消服务端写操作
5. 成功后演示列表更新，支持继续上传；失败时窗口仍打开则保留选择与信息，提示先核对列表再重试，不自动重试；关闭后不保留
6. 页面顶部可切换列表正常/加载/失败/空状态，以及上传成功/失败/停在处理中/总量未知；“停在处理中”可收起窗口后点“模拟处理完成”继续

## 正式上传（2026-10-21）

用户说明后端当前不可达，并明确同意暂按旧逻辑“仅判断 code”实现。`uploadFiles` 复用公共 HTTP 对信封的 `code === 200` 判断，主动丢弃未知 `data` 并返回 void；不统计成功文件数，不解释部分成功。这是临时业务决策，不是接口实测结论，也不改变资源管理的响应契约。

- `api.ts` 创建多文件 FormData，非空备注去掉首尾空白后发送；不传上传人、不另建客户端
- `useUploadFilesMutation` 显式关闭重试；发请求前检查发起会话，成功后只使同一有效会话的文件分页缓存失效，保留当前分类、筛选与页码。列表仍由已有查询控制
- `useFileUpload` 立即防重复；字节进度到 100% 仅进入等待处理，拿到成功响应后才成功。总量未知不显示百分比，加载反馈沿用 `useDelayedFlag`
- 关闭清草稿但不取消写操作；窗口关闭后同会话的完成/失败由入口提示。路由离开后请求继续，同会话缓存仍可失效，旧界面与提示不再更新；重新进入页面不恢复上一页面的任务视图，不实现跨页面任务队列
- 换会话、会话过期、组件卸载后忽略晚到的界面结果与进度；新会话不会被旧上传的成功结果刷新
- `FileUploadDialog` 传送到 body，避免嵌在查询表单内；X / Esc 在用户动作时清草稿，动画完成事件不承担清理

响应待核对项：后端恢复后检查整批或部分成功、成功/失败 data、服务端文件限制及权限。若能部分成功，再按真实契约增加反馈；当前不凭猜测删除失败项或自动重试。没有向真实后端提交测试文件。

本次新增 API、草稿/任务与正式组件测试，覆盖多文件字段、仅 code 的结果、无效/失败响应、防重复、失败保留、关闭清空、未知总量、100% 后等待、卸载、会话切换及同会话缓存失效。原生 multipart 文件名/字节的证据沿用公共基础浏览器测试；jsdom 的 File 与 Node 序列化不兼容，因此本轮单元测试检查交给公共 HTTP 的 FormData，不能把模拟 XHR 的文件名/内容当作浏览器证据。

验证结果：相关 17 个测试文件、150 项测试通过，类型检查、lint、公网构建通过；构建仍只有既存的 crypto 外置及大块提示。分别故意破坏“发送中关闭清文件”“旧会话不刷新缓存”“X 关闭清草稿”，三次均得到预期断言失败，随后恢复并重新通过。本轮未修改共享 HTTP、主题、依赖清单或锁文件。

本次浏览器在本 worktree 的限时 HTTP 服务复查标题、关闭按钮/X/Esc 清空、失败保留和重试入口；正式页面检查空列表、标签选择、关闭清空、空提交校验，尺寸为桌面 1440 × 900、窄屏 390 × 844、矮屏 1440 × 600，底栏可见、内容内部滚动。当前 Chrome 扩展未允许从磁盘选择文件，本轮未更改权限，也未完成正式页面从文件选择器到上传成功的完整浏览器验证；该连接由真实组件 + MSW 测试覆盖。正式后端仍不可达，待恢复后验收。
