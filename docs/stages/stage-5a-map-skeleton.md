## 改动与目的

### 1. 开始前的边界修复（ADR 0026）

阶段四结束后的独立评审指出，二维视图在几种情况下会和会话状态长期不一致。在 MapLibre 6.12 的源码中逐一确认，写出在原实现上失败的测试后再修：

| 问题 | 修复 |
|---|---|
| 整份样式通不过校验时，MapLibre 只发 `error`、不发 `style.load`，视图永远停在 `initializing` | 加载中收到 `error` 判定加载失败，进入 `failed`；出现新版本时自动重新加载 |
| `addLayer` 等方法校验失败时只发 `error` 不抛错，原实现把没加上的版本记为已应用 | 应用命令期间同步收到的 `error` 也触发整体重建；"已应用"只在全部成功或整体加载完成时更新 |
| 首次进入 ready 与恢复显示各自同步相机，初始化期间的相机变化跟不过来 | 统一为一段流程：追上样式 → 跳到会话相机 → 读地图的实际值写回 → 进入 ready |
| Worker 一侧收到无法反序列化的消息时没有通知 | 按崩溃处理（ADR 0025 第 2 条已有规定） |
| 加载失败时会话里已有更新的版本、报错后仍加载完成、激活中追赶失败 | 直接用最新快照重新加载；以 `style.load` 为准恢复快照；中止激活，`whenReady()` 继续等待 |
| `whenReady()` 在恢复显示触发重建时提前成功 | 按一轮整体加载结束 |

| 评审意见 | 修订 |
|---|---|

# 第二部分：可以学到什么

## 一、Vue 的生命周期：读源码确认的顺序

ADR 0028 的设计依赖几条生命周期的顺序，都在 Vue 3.5.43 的源码里确认过：

| 时机 | 顺序 | 用在哪 |
|---|---|---|
| 挂载 | 父组件的 `onBeforeMount` 在渲染子树之前，早于子组件的 setup | 初始样式在画布创建视图之前一次提交 |
| 卸载 | 父组件先 `onBeforeUnmount`，再 `scope.stop()`（`onScopeDispose` 在这里执行），然后卸载子组件，最后自己的 `onUnmounted` | 会话在 `onUnmounted` 释放，晚于子组件里的视图；不能放在 `onScopeDispose` |
| 清理回调 | `scope.stop()` 依次执行，不逐个捕获异常 | 卸载路径上的回调一律 `try/catch`，否则子组件和后续的卸载钩子都不执行 |
| 注入 | `inject` 从父组件开始找，提供上下文的组件拿不到自己 provide 的值 | 悬浮元素的登记要放在子组件里 |
| `app.runWithContext` | 能拿到注入，但没有作用域 | `useMapOverlay` 要另外检查作用域，否则 `onScopeDispose` 只警告、登记注销不掉 |

父组件的 `onUnmounted` 晚于子组件是文档写明的行为；其余几条来自源码，所以都有测试覆盖，Vue 升级时由测试发现变化。

## 二、响应式的边界

- 会话、视图这类引擎对象不进响应式：provide 普通对象，视图放在 `shallowRef` 里只追踪"换了一个视图"
- 对外只读用 `shallowReadonly`，不用 `readonly()`：深层代理会包住引擎对象，私有字段（`#field`）的访问会报错；`shallowReadonly` 包住 `shallowRef` 后依赖追踪照常，赋值被忽略并在开发环境警告
- 只读不只是类型：视图的受限入口是冻结的普通对象，只转发 `kind`、`flyTo`、`fitBounds`，JS 里也调不到释放
- 每帧都变的值按需订阅：相机由 `useCamera()` 在调用方的作用域里订阅，只有用到它的组件每帧更新

## 三、`computed` 抛错之后

5A.2 实测 Vue 3.5.43 中 `computed` 抛错后的行为：

1. 异常在调度器检查依赖是否变化时抛出，读取方的 `try/catch` 接不住，侦听器这一轮不执行
2. 依赖不变时再读取，不再抛错，而是返回上一次成功的旧值

第 2 条最危险：资源换了新年份、高亮的推导出错后，下一次无关的变化会把"新资源 + 旧高亮"当作成功提交。解决办法是把异常变成值——在提交器自己的 `computed` 里用 `try/catch` 调用推导函数，结果是"成功的分组"或"失败"，失败一直缓存到推导用到的依赖变化。这条结论写进了 AGENTS.md：`computed` 不抛异常，可能失败的计算把失败表示成数据。

## 四、跨分组的原子提交

- 合并通知不等于原子提交：`StyleModel` 每次 `setGroup` 当场校验，微任务只负责把通知合并成一次。资源换数据源、高亮改引用，分两次提交时不管谁先，中间状态都引用了不存在的数据源
- 单一提交器：所有绑定的结果在同一轮里用一次 `setGroups` 提交，校验针对组合后的结果
- 失败时整批跳过、记下"上次提交成功的结果"：之后任何变化都连同没提交成功的分组一起重试，最终收敛到最新的合法组合
- 数据流的约定：引用方的推导依赖被引用方的状态，两者才会在同一轮变化。晚一轮时第一轮会被拒绝并报告，这个报告说明数据流写错了
- 校验发现不了业务上的不配套（数据源 ID 不变、年份不配套），只能靠"同一轮变化"和"推导失败整批跳过"保证

## 五、接口的权限

| 拿到什么 | 能做什么 | 理由 |
|---|---|---|
| 页面句柄（`provideMap` 的返回值） | 绑定样式、读取全部状态 | 只有页面组装拥有者 |
| 只读上下文（`useMap()`） | 读视图状态、失败原因、相机；定位；引擎失败后重试 | 子孙组件不能写样式、不能直接写相机 |
| 视图的受限入口 | `flyTo`、`fitBounds` | 暂停、恢复、释放由 map-vue 自己负责 |
| 拥有者 | 只给推导函数 | 不碰会话，不挂地图就能测 |

讨论中一度用过"分组槽"（拥有者拿到只能写一个分组的对象），因为跨分组原子提交的问题放弃了：每个槽各自提交，原子性就没了。

## 六、定位可视区域

- 为什么不用布局常量：界面要后置重新设计，按 `16 + 320 + 16` 算的 padding 换了设计就失效；面板收起、隐藏也要另外处理
- 为什么现量现算：只在定位那一刻需要，用 `getBoundingClientRect` 量一次，量到的总是当下的状态；`ResizeObserver` 测不到"尺寸不变、位置变了"
- 为什么不用 MapLibre 的 `setPadding()`：它会把 padding 留在地图上，`getCenter()` 变成可视区域的中心，破坏"会话相机的中心就是画布中心"，二三维共用相机时也对不上
- 下限：420 宽的画布上左右 padding 共 400，`fitBounds` 缩到 z1.33；保留 1/3 后是 z4.15，目标有一部分落在面板下面，但不至于看不见
- 量的是实际尺寸：`width: 320px` 加左右内边距 16 的面板按 352 算，这正是不用常量的好处

## 七、失败作为数据

ADR 0026 当时没有使用方，决定"原因从 `whenReady()` 取得，不另加 API"。做提示时发现：只有适配器知道走的是哪条失败路径；判断不支持 WebGL2 要用 `instanceof GPUInitializationError`，而 `shared/map` 不能导入 maplibre-gl；界面要和逻辑解耦，原因应该是同步可读的数据。于是写 ADR 0030 修正：`MapView.failure` 只在 `failed` 时有值，状态或原因任一变化都发出 `statechange`。已接受的 ADR 不改正文，原 ADR 只在状态行注明被哪一份修正。

## 九、工作方法

### 1. 评审驱动的 ADR

ADR 0028 提交评审后被指出两处契约问题（原子提交、只读），修订后又被指出两处（推导失败、缓存）。每一处都先在代码或源码里验证，再改设计：`computed` 抛错后返回旧值，就是为了回答"推导失败怎么办"时实测出来的。

### 2. 不确定的事先不定

- 界面：设计稿做出来后发现定不下来，就把界面后置，只保证界面可以整体替换
- 细节：未勾选的图层留不留、Worker 数量、高亮方式等，都写进 roadmap 对应的步骤，到时用真实数据决定

### 3. 在真实环境里验证

- 开发页上逐项验证提交器、定位可视区域、失败提示和重试；420 和 1280 两种宽度
- 生产构建确认入口包里没有 maplibre-gl
- 浏览器面板太窄时截图看不清，改用 DOM 测量各区域的位置；用 `find` 拿元素引用点击，避免坐标换算出错

## 十、替代方案汇总

| 领域 | 本项目选择 | 常见替代 | 没选的主要原因 |
|---|---|---|---|
| map-vue 的位置 | `libs/map-vue`，项目配置在 `shared/map` | `shared/map-vue` | 衔接和项目配置混在一起，map-cesium 拆包时拆不出去 |
| 会话和视图 | 页面 `provideMap`，`<MapCanvas>` 创建视图 | `<MapProvider>` 组件；会话放 Pinia | 页面拿不到子组件的注入、组名查不到；store 深层响应式、同时只能有一张地图 |
| 样式提交 | 页面一处绑定，单一提交器 | 各拥有者提交（分组槽）；提交单元 | 跨分组不原子；卸载时要逐组清空 |
| 推导结果的形式 | 推导函数，提交器包成自己的 `computed` | 接受 `ref` / `computed` | `computed` 抛错后返回旧值 |
| 只读 | `shallowReadonly` + 冻结的受限入口 | `readonly()`；只靠类型 | 深层代理破坏私有字段；类型挡不住 JS 调用 |
| 定位可视区域 | 登记 + 现量现算 | 布局常量；页面自己算；`ResizeObserver`；`setPadding()` | 换设计就失效；容易漏；测不到移动；破坏相机中心的约定 |
| 失败原因 | `MapView.failure` 作为数据 | 从 `whenReady()` 取、按错误类型猜 | 只有适配器知道路径；`shared/map` 不能导入 maplibre-gl |
| 引擎失败的重试 | 上下文的 `retry()` | 页面换画布的 `key` | 每个页面都要管 key |
| 地图页的界面 | 后置到 5D，先做联调骨架 | 现在定稿 | 与旧版区别不大，状态还不全 |
| 测试加速 | `fsModuleCache` + Node 环境 | `vmThreads`、`isolate: false` | 大量测试失败 |
