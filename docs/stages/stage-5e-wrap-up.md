## 改动与目的

### 1. 性能标记与实测脚本（5E.1）

- 标记用浏览器标准的 User Timing：开始（发出登录请求）、`session`、`runtime`、`page`、`view-ready`、`settled`，DevTools 的 Performance 面板能直接看到，留在产物里给三维阶段和阶段七复测
- 视图就绪对应 MapLibre 的 `style.load`，那时瓦片还没到；`settled` 是视图的新事件 `settle`（MapLibre 的 `idle`），只在 `ready` 时发出
- 实测脚本用 Playwright 驱动本机的 Edge（有界面，真实 GPU），CDP 限速，每次新的浏览器上下文；账号密码从环境变量读，由用户在自己的终端运行
- 基线：画面稳定在不限速 1.26 s、Fast 4G 3.33 s、Slow 4G 17.5 s

### 2. 加载策略（5E.2，ADR 0061、0062）

| | Fast 4G 视图就绪 | Fast 4G 画面稳定 | Slow 4G 视图就绪 | Slow 4G 画面稳定 |
|---|---|---|---|---|
| 改动前 | 1.51 s | 3.59 s | 7.06 s | 17.6 s |
| 改动后 | 0.37 s | 2.22 s | 2.04 s | 12.5 s |

- 登录页空闲时用路由的同一个加载函数预加载地图运行时和地图页分块；只在省流量模式时跳过（修正了原则里"2G 时跳过"）
- 进入地图时两个分块同时下载，都到了以后设置运行时、预热 Worker 池（`prewarm()`），Worker 池整个会话保留
- 默认框架由 `defaultMapFramework()` 回答，现在固定是二维；map-vue 的运行时注入留到三维阶段有了第二个框架再做
- 字体不推迟（ADR 0062）：普惠体两个字重各约 5.2 MB、不能子集化，推迟在 Slow 4G 的第一次访问能快 1.6～5.1 s，但每次访问都要多一次字体切换

### 3. 求交库（5E.3）

去掉 `@turf/intersect`（`polyclip-ts`、`bignumber.js`）后地图页分块少 42 KB（gzip 15 KB），Fast 4G 只快 2 ms、Slow 4G 快 138 ms；预加载以后它在输入密码期间就下载完了。决定不按需加载，区划范围仍是同步的。

### 4. 页面缓存（5E.4，ADR 0063）

- `AppLayout` 里常驻一个 `KeepAlive`，路由 meta 写了 `keepAlive: true` 的页面放进去（现在只有现状底图）；回到登录页时布局卸载，缓存清空
- 回到地图约 10 ms 画面就稳定（重建约 550 ms），相机、勾选、点选结果、测量、面板、区划都保留，多约 2 MB 的 JS 堆
- 页面停用时 `MapCanvas` 暂停视图：隐藏期间的定位等恢复后再执行；恢复时先按容器尺寸调整画布；暂停时还在进行的定位动画直接到终点并写回会话
- 两组 Tab 面板把"页面停用"当作隐藏（结束拾取、丢弃取色预览），拖动中的图钉取消，画了一半的框选取消
- 被缓存的页面量尺寸用 `useShownElementSize`：停用期间量到的 0 不采用，恢复的第一帧不按 0 排版

### 5. 整体走查（5E.5）

- 旧仓库 `master-demo` 仍是 `6b4799b`，地图相关的路径和基线 `836f03b` 相比没有改动

# 第二部分：可以学到什么

## 一、实测的方法比数字更重要

- **"禁用缓存"不等于第一次访问**：禁用缓存时 MapLibre 的 4 个 Worker 各下载一次 Worker 脚本，Slow 4G 下画面稳定晚约 2 秒。第一次访问是"缓存为空、照常工作"：每次用新的浏览器上下文就够了
- **先确认限速对谁生效**：MapLibre 在 Worker 里下载省界和矢量瓦片。先用一个小页面实测了页面级的 CDP 限速对专用 Worker 里的 `fetch` 同样生效，否则 Slow 4G 的数字会偏小
- **对比要交替测量**：几份构建在同一轮里按"每档网络的第 i 次依次测完所有构建"进行，网络的波动平均分到每一份上，不会集中在某一份
- **复测一次看稳定性**：基线 15 分钟后复测只差几十毫秒，所以对比实验每组 3 次就够
- **看各段的耗时，不只看总时间**：两个分块先后下载、省界要等 Worker 脚本、字体分带宽，这些都是从"各段的耗时"和"资源的完成时刻"里看出来的
- **测量的环境要说明**：预览服务器的压缩和生产一样，缓存头不一样；应用内浏览器的窗格在后台时动画帧暂停，量出来的时间不可信

## 二、加载：瀑布、预加载与预热

- `await import(a); await import(b)` 是瀑布：b 要等 a 下完才开始。页面模块执行时不创建地图，所以运行时的设置放在两者都到了之后也来得及，两个分块可以同时下载
- 预加载用 `import()` 而不是 `<link rel="prefetch">`：模块会立即执行，路由导航时直接从模块表取用；代价是地图页分块的顶层代码在登录页上执行（实测没有长任务）
- 预热 Worker 池和预加载抢同一段带宽：实验里运行时一到就预热，Slow 4G 下视图就绪晚了 0.8 秒；改成两个分块都到了再预热
- 预加载真正起作用的是第一次访问和每次部署后的第一次访问；之后靠带 hash 的长期缓存（阶段七）

## 三、KeepAlive 的几个行为

- 停用时组件的 DOM 被移进一个不在文档里的容器：`ResizeObserver` 随即报出 0；MapLibre 量到容器宽高为 0 时用默认的 400×300
- 恢复时 `onActivated` 先于 `ResizeObserver` 重新量：激活钩子里读到的还是停用期间量到的尺寸。所以要么停用期间不采用测量（`useShownElementSize`），要么恢复时同步量一次（`MapLibreView.resume` 里的 `map.resize()`）
- Element 的下拉、取色器这类 Teleport 到 `body` 的弹出层，在切走时自己收起，不会留在别的页面上
- 被缓存的组件仍然响应数据变化、仍然重新渲染（渲染到不在文档里的 DOM 上）：隐藏期间晚到的识别结果、区划边界照常写入
- `onActivated` 在第一次挂载时也会调用；`MapCanvas` 只在停用过以后才恢复视图

## 四、暂停与相机

- 视图的"暂停"本来是给二三维切换准备的：另一个视图在显示，暂停的视图不接收输入、不把地图的移动写回会话，恢复时按会话的相机同步。页面缓存直接复用它，相机操作"等就绪再执行"的规则也不用改
- 真实页面上才发现的问题：区划定位在切走之前就开始了（市界已经下载过），暂停时动画还在进行，暂停期间的移动不写回，恢复时又同步回了动画中途的位置。修法是暂停时把进行中的定位动画直接放到终点、在进入 `paused` 之前写回会话。以后切到三维时，三维也从定位的终点开始
- 二三维共用的规则在单一场景里很难测全：这次是页面缓存把"暂停时正在动画"这个场景带了出来

## 五、测试

- **假对象太理想会藏住缺陷**：假地图的定位瞬间到位，测试永远碰不到"暂停时动画还在进行"。补了动画模式（带时长的定位先不到位、可以被打断），真实引擎上再用浏览器测试确认
- **模块级的缓存会让用例互相影响**：市界在模块里只下载一次，"停用期间边界才到"要用新的模块（`freshModules()`）才测得到
- **改坏验证先确认基线通过**：有一次补的断言本身就是错的（暂停后图钉不渲染，拿住的旧元素不会更新），改坏"测出"是因为基线就失败了。之后先跑基线，再改坏
- **等价的改法不算缺陷**："图钉在停用时取消"和"在激活时取消"对用户没有区别，这样的改坏测不出来是对的
- **评审用例**：工作区里另有人补了两个探测用例（框选草稿、激活后的排法），都在实现上失败、都指出了真实的问题；修掉以后按项目的写法整理进正式测试

- 需要真实账号的实测由用户在自己的终端运行，脚本只从环境变量读账号密码；我用本地的假后端（假的 JWT、空的资源目录）试跑脚本本身

## 七、替代方案汇总

| 领域 | 本项目选择 | 常见替代 | 没选的主要原因 |
|---|---|---|---|
| 耗时的记录 | User Timing，留在产物里 | 只在实测时临时加日志 | 三维阶段和阶段七还要复测；标准接口，DevTools 直接显示 |
| 实测方式 | Playwright 脚本、CDP 限速、交替测量 | DevTools 手测 | 不能重复，难取中位数，难比较几种做法 |
| 第一次访问的模拟 | 新的浏览器上下文 | 禁用缓存 | 禁用缓存时 4 个 Worker 各下载一次脚本 |
| 预加载 | 登录页空闲时 `import()` | 不预加载、登录时显示加载状态；`<link rel="prefetch">` | 下载必然排在登录之后；prefetch 拿不到带 hash 的分块地址，也不执行 |
| Worker 池 | 两个分块都到了再预热 | 运行时一到就预热；不预热 | 前者和页面分块抢带宽；后者省界要等 Worker 脚本 |
| 字体 | 不推迟 | 推迟 SemiBold 或两个字重；只在第一次访问推迟 | 每次访问都有字体切换；第一次访问的记录和浏览器缓存可能对不上 |
| 页面缓存 | 常驻 `KeepAlive` 加路由 meta | `include` 组件名；不缓存、回来时恢复状态 | 组件名要和路由对上；每种状态都要另存再恢复 |
| 隐藏期间的视图 | 暂停（复用二三维切换的规则） | 什么也不做、恢复时 `resize()`（旧项目） | 隐藏期间的定位按错误的尺寸算 |
| 恢复的第一帧 | 停用期间不采用测量 | 恢复后等 `ResizeObserver` | 按 0 排的界面会闪一下 |

## 形成的结构

- **map-core**：地图会话是二三维共同的唯一真相源，持有样式模型（按分组推导、整体替换）、相机（相机操作的信号判断作废）、工具模型（同一时间一个当前工具）、选择状态；MapLibre 适配器是唯一能写二维地图的地方，状态转换、数据源错误、暂停与恢复都在它里面
- **map-vue**：`provideMap` 创建会话和上下文，`bindStyle` 把拥有者的推导函数绑定到分组，`MapCanvas` 管视图的创建、重建、暂停；上下文给出就绪的视图入口、相机操作、悬浮元素的可视区域、鼠标位置
- **shared/map**：与业务无关的公共能力（底图、行政区、默认视角、工具栏、测量、区划定位与裁剪、坐标定位、状态栏、面板组、浮层），按"拥有者"写：组合式函数持有状态、纯函数推导分组
- **features/resource-map**：资源图层、面板、图例与符号、点选与框选、年份
- **页面**：现状底图只挑选、组合这些能力；加载由 app 的 `withMapRuntime` 和登录页预加载负责，页面切走时由布局缓存

## 做得好的

- **界面与逻辑分开**：5A～5C 把当前工具、面板开关、失败原因都做成数据，5D 替换界面时拥有者基本不动
- **先实测再定方案**：Worker 数量、未勾选的图层、地类统计、点选的识别、区划裁剪、加载策略都是测过真实数据以后才定的，好几处推翻了最初的设想
- **规则先统一**：5C 开始前插入的地图内核加固（异步的作废规则、相机操作对象、状态转换表），让之后的定位、点选、区划、页面缓存都按同一套规则判断"结果还算不算数"
- **改坏验证**：每一步都故意改坏、确认失败原因是断言，前后补强了很多"看起来测到了、其实没测到"的用例

## 可以做得更好的

- **假对象太理想**：几乎每个子阶段都在真实页面上发现单元测试没覆盖的问题（MapLibre 的校验、`ResizeObserver` 的反馈、暂停时的动画）。浏览器测试（ADR 0040）补上了一部分，真实页面的验收仍然不能省
- **ADR 的事实要核对**：ADR 0063 的背景把实验日志里容器的尺寸当成了画布的尺寸，接受以后不能改，只能在文档里更正
- **还原改动要用备份**：5E.1 时用 `git checkout` 还原改坏的文件，连同本次的改动一起丢了，从备份找回；之后都从改动前的备份还原
