# 第二部分：可以学到什么

## 一、Vue 3

### 1. 组合式函数：Vue 里的"自定义 Hook"

React 的自定义 Hook 在 Vue 里叫组合式函数（composable），也用 `useXxx` 命名，思路相同：把有状态的逻辑抽出来，组件只负责渲染。区别来自两者的执行方式：

| | React 自定义 Hook | Vue 组合式函数 |
|---|---|---|
| 执行次数 | 每次渲染都执行 | 只在 `setup` 中执行一次 |
| 依赖 | 手写依赖数组，写漏会读到旧值 | `computed`、`watch` 自动收集依赖 |
| 调用限制 | 不能放在条件和循环中 | 没有顺序限制；用到生命周期或 `inject`（`useRouter` 也是）时，必须在 `setup` 的同步阶段调用 |
| 返回值 | 普通值 | `ref`，是活的引用；解构 `reactive` 会丢失响应性 |

本项目的登录分三层：`useLoginForm`（数据、校验规则、提交）不渲染、不跳转、不弹提示；`LoginForm` 负责界面和提示；`LoginPage` 负责布局和跳转。和 store 的约定一致：越底层越不依赖界面。

测试组合式函数：不依赖组件时，放在 `effectScope` 里运行，`scope.stop()` 相当于组件卸载（`useDelayedFlag` 的测试）；依赖组件（例如要绑定 `ElForm`）时，写一个很小的宿主组件。

### 2. `computed` 不会因为时间流逝重新计算

`isActive()`（token 是否过期）写成方法而不是 `computed`：`computed` 只在它读取的响应式数据变化时重新计算，`Date.now()` 不是响应式数据。写成 `computed` 的话，token 过期后它仍返回第一次算出的结果。这一点实测过。

### 3. store 的解构

- 读取 state 和 getter 要用 `storeToRefs`，直接解构得到的是当时的值，不会随后续变化更新
- 反过来，只需要当时的值时（例如每次请求读取 token），直接写 `useSessionStore().token`，避免被误看成"解构忘了 `storeToRefs`"

### 4. 路由

- **`to.meta` 是父子路由 meta 的浅合并**，同名字段以子路由为准。所以 `roles` 写在父路由上会作用于全部子路由（已实测）
- **守卫中的重定向加 `replace: true`**：例如在现状底图点了没有权限的页面，重定向回现状底图时不会在历史记录里多留一条
- **守卫里使用 store**：pinia 先于 router 安装，首次导航开始时已经能取到 store
- **导航用 `RouterLink`**：渲染成 `<a href>`，可以在新标签页打开、右键复制地址；按钮只用于不跳转的操作

## 二、TypeScript

### 1. 让类型检查替你记住规则

| 写法 | 例子 | 效果 |
|---|---|---|
| `Record<Role, X>` | `roleHome`、`roleLabel` | 新增角色时漏配，类型检查报错 |
| 可辨识联合类型 | 导航项 `NavLink \| NavDropdown`，用 `kind` 区分 | 判断 `kind` 后自动收窄到对应的类型 |
| 类型守卫 `value is Role` | `isRole` | 不用 `as` 断言就能把 `unknown` 收窄 |
| 常量对象 + 同名类型 | `RouteName`、`Role` | 代替 `enum`，符合 `erasableSyntaxOnly` |
| 注册表键推断 | `IconName = keyof typeof icons` | 图标名写错时报错；删除图标后引用处报错 |

### 2. 外部数据先校验再使用

接口返回、localStorage、环境变量都是"外部数据"：

- 接口：每个请求传 zod schema，返回值类型由它推断
- localStorage：会话读取时按 `sessionSchema` 校验，损坏或旧格式的数据直接丢弃
- 环境变量：`appConfig` 在启动时校验，SM2 公钥还校验格式

zod 的两个细节：`.nullish()` 同时接受 `null` 和缺失（Java 后端常返回 `null`）；`z.number().transform(String)` 在校验的同时转换类型，推断出的类型跟着变。

### 3. 接口函数是"防腐层"

`login()` 返回应用自己定义的 `Session`，而不是后端的原始结构：`roleCode` 转成 `role`，数字 `id` 转成字符串，缺失的登录名有兜底。后端改字段名时只需要改 `api.ts`。这种在边界上隔离外部模型的做法叫防腐层（anti-corruption layer）。

### 4. 库的类型不对时

`ElMessageBox.confirm` 的返回值被 Element 声明成"对象与字符串的交叉类型"，现实中不存在满足它的值。测试里做一次类型断言，并写注释说明原因；不要为此关闭整条 lint 规则。

### 5. TSX 中组件不接受未声明的属性

`ElForm` 没有声明 `onSubmit`，TSX 的类型检查不接受。可选的做法：对象展开绕过（等于关掉检查）、全局扩充类型（影响太大）、换一个有类型的事件（在输入框上监听 `keydown`）。本项目选了最后一种。

## 三、架构设计

### 1. 依赖倒置

`shared/http` 需要 token、401 跳转、错误提示，但这些属于上层（鉴权、路由、UI）。做法是 `shared/http` 只定义回调接口，`app/http.ts` 在启动时注入。同样的思路：`setupHttp(router)` 把 router 作为参数传入，测试时换成内存路由；图标工具的 `fileSystem` 参数让测试能模拟"文件已被别的进程改名"。

### 2. 权限只维护一份

页面权限写在路由的 `meta.roles` 上；路由守卫读它，导航菜单也读它（`router.resolve({ name }).meta.roles`）。旧项目维护了两份：按角色的路径清单，以及按角色写死的菜单。`routes.test.ts` 把公开页面和限定角色的页面逐个列出来，误加 `public` 会让测试失败。

### 3. 放在哪一层

| 问题 | 结论 |
|---|---|
| 会话放 `shared` 还是 `features/auth`？ | `shared`：路由守卫、HTTP、布局都要用，它们不属于 auth 这个 feature，而 features 之间不能互相导入 |
| 密码加密放在接口函数还是表单逻辑？ | 接口函数：怎么加密是和后端的约定，表单只处理明文 |
| 登录页的背景图放在哪？ | 和页面放在一起（`pages/login/images/`）：只有登录页使用，删除页面时一起带走 |
| 通用的加载延迟放在哪？ | `shared/composables`：和业务无关，表格、按钮都会用 |

### 4. 生成的结果提交进仓库，用测试检查是否过期

系统名称轮廓、图标注册表都是"由工具生成、结果提交"的：

- 开发时由 Vite 插件自动生成，开发者无感
- 生成的 JSON 提交进仓库，构建和 CI 不需要字体文件、不需要跑工具
- 测试以检查模式运行，发现"改了输入但没重新生成"

这比"每次构建时生成"更稳：CI 中没有字体文件（授权不允许公开），也能完整检查。

### 5. workspace 内部包

`@yzt/icons` 的 `exports` 直接指向 `src/index.ts`，由使用方的 Vite 编译，不需要单独构建、不需要发布。代价是包只能在本仓库内使用；要发布时再加构建步骤。Node 工具放在单独的 `./tools` 入口，浏览器代码不会引入 SVGO。

## 四、工程化

### 1. CommonJS 与 ESM 的互操作

阶段二最隐蔽的问题：Element 的表单校验在测试中永远通过。原因链条：

1. Vitest 默认把 `node_modules` 交给 Node 直接加载
2. element-plus 的 ESM 代码 `import AsyncValidator from 'async-validator'`；async-validator 没有 `exports` 字段，Node 按 `main` 加载 CommonJS 版本，默认导出是整个 `module.exports`（`{ default: Schema }`）
3. `new AsyncValidator()` 抛出 `TypeError`；Element 把它当作"没有出错的字段"，判定校验通过，控制台没有任何输出

浏览器中由 Vite 打包，走 ESM 版本，不受影响。修复：`test.server.deps.inline: ['element-plus']`，让 Vitest 处理 element-plus，它对 async-validator 的导入会经过 Vitest 的兼容处理。试过依赖预构建，无效。

### 2. glob 的细节

micromatch（boundaries 插件用它匹配导入路径）：

- `**` 不匹配以点开头的路径段，所以 `../**` 匹配不了 `../../a`；改成 `@(./|+(../))**`
- `./` 会被规范化掉，所以不能写 `./**`（阶段一发现）
- 数组形式的结果和预期不同，不能用
- `@/**` 只匹配 `@/` 别名，不会误匹配 `@yzt/*`、`@element-plus/*`

每次修改都先用 micromatch 单独验证，再用 lint 探针验证。

### 3. 换行符

Windows 上 git 的 `core.autocrlf=true` 会在检出时把 LF 改成 CRLF。工具写出的文件是 LF，比较已有文件时要先统一换行符，否则全新 clone 后检查会把所有图标误报为"未处理"。复现方法：在临时副本里把文件改成 CRLF 再跑检查。

### 4. 图片

- **倍率看屏幕的物理宽度**，与 Windows 缩放无关：1080p 屏（任何缩放）物理宽 1920，2K 屏 2560，4K 屏 3840。全屏背景用 2x 能覆盖到 4K
- **webp 有损压缩**：旧的 1920×1080 PNG 2 MB，同样内容的 webp（质量 80）71 KB；3D 渲染图不要用无损
- **放在源码目录并由 Vite 引用**：构建时文件名带内容哈希，可以长期缓存；`public/` 下的文件没有哈希
- **只在需要时加载**：插画的背景图只写在宽屏的媒体查询里，窄屏不会下载

### 5. 开发服务器的副作用

- 同时开着多个开发服务器时，它们都会处理图标目录；一个先改了文件名，另一个再改就会遇到"文件不存在"，最初这让服务器直接退出。现在跳过这种文件、捕获所有异常、合并连续事件
- 修改 `vite.config.ts` 引用的文件（例如文字轮廓的清单）会让开发服务器重启并重新生成文件。做"改坏配置看测试是否失败"的验证时，要注意生成的文件已经被开发服务器同步更新，验证可能失效；改为直接修改生成结果来模拟过期
- `pnpm install --force` 在开发服务器运行时，会因为 sass 的 `dart.exe` 被占用而失败，并删掉它的二进制

## 五、浏览器与界面细节

### 1. 自动填充

- **背景色**：Chrome 的浏览器样式表对自动填充的输入框设置了带 `!important` 的背景色。浏览器样式表的 `!important` 优先级高于页面的 `!important`，页面改不回来。用与输入框同色的大面积内阴影盖住它；颜色取自 Element 的 `--el-input-bg-color`，它从外层继承下来，一条规则适配所有输入框
- **字体**：页面加载时自动填上的账号密码在用户交互前只是"建议值"，页面的 JS 读不到，字体由浏览器固定。Chromium 源码的注释说明了原因：如果建议值使用页面的字体，页面可以为每个字符准备一个字体文件，从下载了哪些文件推测出密码。这是安全设计，不应覆盖
- **校验状态**：只写 `trigger: 'blur'` 时，自动填充写入未聚焦的输入框不会失焦，之前的错误提示会一直留着；改为 `['blur', 'change']`

### 2. 输入法

用中文输入法选字时按的回车，`KeyboardEvent.isComposing` 为 `true`，不能当成提交。

### 3. 加载状态

请求很快完成时，加载样式一闪而过就是"抖动"。常见做法：超过 300ms 才显示；一旦显示至少保持 400ms。防重复提交的标志仍然立即生效，和显示分开。另外，加载图标出现时不应推动文字：用负外边距抵消图标的宽度。

### 4. 响应式：先量再定断点

顶部栏的断点不是拍脑袋定的：分别测量 Logo、系统名称、导航、用户区在各档下需要的宽度，再定 1680 / 1440 / 1200。换了素材后重新测量。同样，判断渐变色是否符合主题色，先把颜色换算成 HSL 比较色相，再并排对比实际效果；数字和观感的结论不同时，以衔接的实际效果为准。

### 5. 小问题

- 全局没有 `box-sizing: border-box` 时，`min-height: 100vh` 加上内边距会出现滚动条
- 视口模拟在尺寸大于窗格时截图会出错；需要看大屏效果时，把大尺寸页面放进 iframe 再缩放显示

## 六、安全

| 问题 | 处理 |
|---|---|
| 旧前端写着 SM2 私钥（与登录用的公钥配对） | 不迁移私钥和解密函数；建议后端更换密钥对，公钥放 `.env` 便于更换 |
| 旧前端写死 AI 后端的账号密码 | 不迁移；迁移 AI 对话时和后端商量由主后端换发 token |
| 旧"记住密码"把明文 base64 存在本地 | 删除该功能 |
| token 放 localStorage，被注入脚本时可读 | 与旧项目一致；更安全的 httpOnly Cookie 需要后端改造（ADR 0015 记录了这个代价） |
| 前端判断 token 过期但不校验签名 | 只用于提前跳转登录页，真正的鉴权在后端 |
| sm-crypto 停更多年后一个月内连发多个版本 | 查了发布者和安装脚本，没发现投毒迹象；最终选了 sm-crypto-v2 |
| `VITE_` 变量写进产物 | 只放公开信息（SM2 公钥是公开的） |
| 字体授权不允许公开发布 | 字体不入库，仓库是公开的 |

## 七、工作方法

### 1. 故意改坏，确认测试会失败

阶段二每一步都做了变异验证：逐个改坏源码，确认有测试失败。几次有价值的发现：

- "再次开始时重新计时"最初没有测试能发现，分析后发现是一个有意设计的行为没有被写成用例，补上了
- "角色写死"的第一次改法引用了未导入的变量，失败原因是代码报错而不是断言，换了改法重测
- 表单校验"永远通过"是写组合式函数测试时发现的：本该失败的用例通过了

### 2. 先写能复现问题的测试

修复"自动填充后残留的校验错误"时，先写一个测试，确认它在修复前失败，修复后通过。这样测试证明的是"问题被修好了"，而不只是"代码能运行"。

### 3. 纠正自己说错的话

2.9 讨论选型时说"旧代码用 `atob` 解析 JWT 遇到中文会出错"，写 ADR 前实测发现它不报错，只是得到乱码（`exp` 正确），于是在 ADR 和汇报中按实测结果更正。文档里的每个行为说明都先实测再写。

### 4. 拿不准的东西去查源头

自动填充的字体能不能改？与其猜测，不如直接看 Chromium 的浏览器样式表源码，规则和原因都写在那里。同样，Element 表单校验的问题靠读 element-plus 的源码一步步定位。

### 5. 不能自动化验证的，说清楚

浏览器的真实自动填充、用真实账号登录，自动化工具做不了（也不应该用凭据去登录）。这类验证交给用户，并说明模拟验证做到了哪一步。

## 八、替代方案汇总

| 领域 | 本项目选择 | 常见替代 | 没选的主要原因 |
|---|---|---|---|
| 路由 | 手写路由表、history 模式 | 文件路由；hash 模式 | 文件路由的 `definePage()` 只能用在 SFC 中，且依赖编译期生成代码；hash 被路由占用，history 只需部署时由服务端回退到 `index.html`（ADR 0007） |
| 状态管理写法 | setup store | options store | 与组合式 API 一致 |
| 测试 DOM | jsdom | happy-dom | 速度相当，规范实现更完整（ADR 0010） |
| HTTP 请求库 | axios | ky、原生 fetch | 上传进度可靠（ADR 0011） |
| 返回值校验 | zod 4 | valibot、手写类型守卫 | 生态最大；手写难维护 |
| 接口模拟 | MSW | `vi.mock('axios')` | 与请求库解耦 |
| 标题字体 | SVG 轮廓 | 加载 1.4 MB 字体；子集化 | 授权与体积 |
| 图标 | 内联 SVG + 生成的注册表 | 雪碧图（vite-plugin-svg-icons） | 后者已不维护，需要把所有图标注入 DOM |
| 图标包形式 | workspace 内部包 | 放在应用里；发布的独立包 | 可复用，又不需要构建和发布（ADR 0014） |
| SM2 | sm-crypto-v2 | sm-crypto | 自带类型和 ESM，底层是审计过的 `@noble/curves` |
| token 过期 | jwt-decode | 手写解析；不在本地判断 | 手写容易出错；不判断则要等请求失败才跳转 |
| 会话存储 | localStorage | sessionStorage；httpOnly Cookie | 与旧项目一致；Cookie 需要后端改造 |
| 页面权限 | 路由 `meta.roles` | 按角色的路径清单 | 权限只维护一份 |
| 两级下拉 | ElPopover + 自定义面板 | ElMenu 水平模式的子菜单 | 还原旧项目的两列面板 |
| 自动填充背景 | 同色内阴影 | 很长的 `transition` | 后者依赖计时和实现细节 |
| 加载状态 | 延迟显示 + 最短保持 | 与请求同步切换 | 快速请求时闪烁 |
| 表单校验在测试中生效 | `server.deps.inline` | 依赖预构建 | 预构建无效（已实测） |
