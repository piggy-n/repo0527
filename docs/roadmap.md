# 路线图

整个重构分为 8 个阶段。本表在阶段零制定（当时只写在会话中，2026-09-30 补成本文），此后每个阶段结束时更新"状态"和"调整"两部分；原来的"内容"和"主要学习点"保留，便于对照计划与实际。

阶段五开始时（2026-10-09）把阶段五拆成 5A～5D 四个子阶段（5A.3 时加入界面设计，改为 5A～5E 五个），并在阶段五、六之间加入单独的三维阶段。三维阶段不编号：ADR 和各文档里的"阶段六""阶段七"保持原来的含义。

## 阶段总览

| 阶段 | 内容 | 主要学习点 | 状态 |
|---|---|---|---|
| **0. 约定** | `AGENTS.md` 骨架（分层、依赖方向、命名），确认待定问题 | 架构分层、依赖倒置 | ✅ 完成（ADR 0001、0002、0004） |
| **1. 工程基础** | `apps/web`：Vite 最新版 + `plugin-vue-jsx` + TS strict；tsconfig 分层；实测 TS 7 工具链；lint（只管正确性，格式交给 WebStorm）；Vitest | tsconfig 各项配置的含义、`jsxImportSource: 'vue'`、Vite 插件管线 | ✅ 完成（tag `stage-1`，[总结](stages/stage-1-engineering-foundation.md)） |
| **2. 应用骨架** | 有类型的 HTTP 客户端和错误模型、鉴权、路由守卫（用模块扩充给 `RouteMeta` 加类型）、布局、存储适配器、MSW、Element Plus 主题、CSS Modules | 泛型、可辨识联合、模块扩充、Adapter 和 Strategy 模式 | ✅ 完成（tag `stage-2`，[总结](stages/stage-2-app-skeleton-and-auth.md)） |
| **3. 第一个纵切** | 登录 + 布局 + 一个简单列表页，把 API、query、store、TSX 组件、测试整条链路跑通 | vue-query（TanStack Query），TSX 中 props、emits、slots 的类型写法 | ✅ 完成（tag `stage-3`，[总结](stages/stage-3-layout-and-first-list.md)）：页面布局规范与 `libs/ui`（ADR 0016）、文件管理列表（ADR 0017）、会话结束的统一处理 |
| **4. map-core** | 重新设计引擎抽象、Manager 体系、有类型的事件、有类型的 Worker 消息、资源释放 | 接口与抽象类的区别、Facade、Factory、Observer、`using` / Disposable | ✅ 完成（tag `stage-4`，[总结](stages/stage-4-map-core.md)）：地图会话与 MapLibre 适配器（ADR 0018～0024）、Worker 通信层（ADR 0025） |
| **5. map-vue + 现状底图** | `MapProvider`、`useMap()`、图层面板 | provide / inject 的类型、响应式边界（`shallowRef`、`markRaw`） | ✅ 完成（tag `stage-5a`～`stage-5e`，各子阶段一篇总结，[阶段五回顾](stages/stage-5e-wrap-up.md#阶段五回顾)）：5A 地图骨架、5B 公共地图能力、5C 现状底图业务、5D 地图页界面的专门设计、5E 收尾（加载策略与页面缓存，ADR 0061～0063） |
| **三维** | map-cesium：Cesium 运行时、样式镜像与三维样式的支持清单、相机同步、三维拾取与测量、瓦片数据服务与 Worker 池；三维独有功能（漫游、钻地、室内地图、本地 3D Tiles）的迁移范围到时再定 | 接近无感的二三维切换、对象池与 Worker 调度 | 暂缓（2026-10-20）：重新调研和设计后再推进 |
| **6. 复杂业务** | 空间监测三件套、AI 流式对话、文件管理，以及其余业务模块 | 拆分巨型组件、流式读取与 SSE、取消请求 | 准备中（2026-10-20）：首批并行补完文件管理、迁移资源管理；消息中心暂不纳入 |
| **7. 收尾** | Playwright、产物分析、部署 | — | 未开始 |

**为什么第 3 步先做简单页面，再做地图？** 地图内核会用到 HTTP、鉴权（瓦片请求要带 token）和错误处理。这些基础设施先在简单页面上验证，比直接放进最复杂的代码里验证风险小得多。学习顺序也更平缓：先掌握 TS 和 TSX 的基础，再进入以面向对象为主的地图部分。

**同步旧仓库的做法**：每迁移一个模块，在 [migration.md](migration.md) 记下对应的 yzt commit 作为基线，以后用 `git diff <基线>..master-demo -- <路径>` 查看旧项目在这个模块上的新改动。（原计划记在 AGENTS.md，阶段二改为单独的 `migration.md`；比较对象用 `master-demo` 而不是 `HEAD`，因为旧仓库可能停在其他分支上。）

### 5C.7 区划裁剪

2026-10-14，[ADR 0051](adr/0051-region-clip.md)。读旧的 `MapRegionLayerFilter`（从瓦片采样探测区划字段、按代码前缀过滤）、`MapRegionClipManager`（过滤不了的图层用挖洞的遮罩盖住）和点选里的区划判断，实测 183 个瓦片集的字段和后端的查询（见 migration.md"区划裁剪的实测"）后讨论确定：业务数据的区县代码和区划目录对不上（崇川区合并前的旧代码、7 个功能区代码），不按属性过滤；区划外用不透明遮罩盖住，点选、框选按区划几何限定范围。评审补充：遮罩按环的嵌套深度构造（洞里属于区划的小岛不被盖住）；渲染要素先按范围过滤再去重、计数，有范围时查询取几何；发给后端的几何误差不超过 2 个像素、通过有效性检查、最多尝试 5 次，做不到时提示范围太复杂。

步骤：

- 5C.7a：`shared/map/region` 的遮罩分组推导和区划范围的几何判断（点在区划里、和区划求交、是否相交），本地边界数据的嵌套检查；现状底图页绑定 `region-clip` 分组
- 5C.7b：点选、框选接入范围（过滤在去重前、取几何、估数用求交范围的外包框），查后端几何的舍入、简化与有效性检查，"范围太复杂"的状态，范围变化时关闭结果
- 5C.7c：真实数据验收（ADR 0051 第 6 节）

5C.7a 完成：`shared/map/region` 加遮罩的推导 `regionClipGroup` / `clipMask`（按环的嵌套深度构造，方向按深度重新定，判断包含时跳过相接的顶点）和区划范围的几何判断 `scopeContains`、`clipToScope`、`intersectsScope`；区划定位加 `readyBoundary`，区划轮廓也改用它；测试检查本地边界数据满足遮罩的前提（只有吴中区有一个洞）；现状底图页加 `region-clip` 分组。改坏验证全部测出，其中"洞和外环相接时挂错了地方"只看点的判断测不出来（判断点也按奇偶规则），补上了结构的比较。浏览器里选吴中区，184 个取样点的遮罩和县界逐点一致

5C.7b 完成：`features/resource-map/query-geometry.ts` 把求交范围整理成发给后端的几何（容差 0、¼、½、1、2 像素依次尝试，舍入到 6 位小数、去掉退化的环，不超过 120 个坐标，自己写的有效性检查把坐标换成整数微度后精确判断相交、相接、共线重叠和折回，都不通过时是"范围太复杂"）；`planIdentify`、`planBox` 接收区划范围（不传时用函数重载保证一定有结果）：落在遮罩上为 null，渲染要素先按求交范围过滤再去重、计数，估数用求交范围的屏幕外包框；拥有者加"范围太复杂"状态，落在遮罩上和范围变化时关闭结果；面板显示提示；页面传入 `readyBoundary` 的几何。比 ADR 多了 `@turf/bbox-clip`：求交前先按外包矩形裁掉区划远处的边，南京市界的求交从约 140 ms 降到 1～20 ms（随机 400 个框验证结果相同）。用真实市界写的测试发现多部分的市界（南京、连云港）裁剪后有空的部分、求交报错，已修复；`roundPolygonal` 展开洞的错误由类型检查发现，先补了能复现的测试。改坏验证全部测出（四个对称子句只去掉一个时其余的仍能拦下，整段去掉时测出）。耗时和体积见 modules/shared-map.md"区划裁剪"。后端返回 502，真实数据验收留到 5C.7c

| 事项 | 决定 |
|---|---|

5E.4 页面缓存（2026-10-16）：

- 实测（本地临时包一层 `KeepAlive`，不提交）：停用时 MapLibre 把画布缩成 0×0、视图仍是 `ready`；隐藏期间执行的区划定位落错了位置（7 级、没有避开面板）；在别的页面按 Esc 不影响地图；下拉、取色器在切走时自己收起；状态都保留。回到地图：重建约 550 ms 画面稳定，缓存约 10 ms；缓存多约 2 MB 的 JS 堆（无界面的 Edge、本地假后端）
- [ADR 0063](adr/0063-map-page-keep-alive.md)（用户按初稿接受）：路由 meta `keepAlive` 加布局里常驻的 `KeepAlive`；停用时暂停视图，恢复时先按容器尺寸调整画布；面板内容按隐藏处理；拖动中的图钉取消
- 实现：`AppLayout` 的 `KeepAlive`、`RouteMeta.keepAlive`（现状底图）；`MapLibreView.resume` 先 `map.resize()`（`MapLike` 加 `resize`）；`MapCanvas` 在 `onDeactivated` / `onActivated` 暂停、恢复视图；`shared/composables` 的 `usePageActive`，两组 Tab 面板和图钉用它
- 评审用例（工作区里另有人补的两个探测用例，用户决定修掉并收进正式测试）：视图暂停时点选的拥有者取消画了一半的框选、工具不变；页面停用期间量到的 0 让恢复的第一帧按错误的尺寸排版，新增 `useShownElementSize`（停用期间的测量不采用），地图页里的 `useElementSize` 都换成它，资源面板手写的尺寸监听同样判断
- 实现中的调整：
  - ADR 的背景写的是"MapLibre 把画布缩成 0×0"，实际是实验日志打印了容器的尺寸；MapLibre 量到容器宽高为 0 时用默认的 400×300。结论不变：隐藏期间画布的尺寸不对
  - 真实页面上区划定位刚开始就切走，回来后停在动画的中途：市界已经下载过，定位在切走之前就开始了，暂停的视图不再把动画的移动写回会话，恢复时又按会话的相机同步。改为暂停时进行中的定位动画直接到终点并写回会话（`MapLike` 加 `moveend`）。单元测试的假地图原来瞬间到位，加了动画模式
  - 测试里的 `readyCachedPage` 用新的模块：市界在模块里只下载一次，否则测不到"停用期间边界才到"
- 改坏验证 21 处全部由断言测出：其中 2 处起初没测出（资源面板的尺寸监听没有测试、动画结束时的清理被另一个用例掩盖），补了浏览器测试、拆开了用例；"图钉在激活时才取消"对用户没有区别，不算缺陷。浏览器测试在真实的 MapLibre 上确认恢复时调整尺寸、暂停时动画到终点，在真实的 `ResizeObserver` 上确认停用期间的 0 不采用
- 真实页面（1440 × 860，已有的会话）：点"无锡"后立即切到文件管理，回来时定位在无锡（10 km 比例尺）、避开两侧面板；切走再回来，区划、面板、图例的位置都在。拖动中切走、退出再登录没有在真实页面上操作（要按住鼠标切页面、要输入账号），由单元测试覆盖
