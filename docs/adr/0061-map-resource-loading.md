# 0061. 地图资源的加载策略：登录页空闲时预加载地图页，预热 Worker 池

- 状态：已接受
- 日期：2026-10-16
- 落实 [map-core.md](../modules/map-core.md)"地图资源的加载策略"的原则（2026-10-09），修正其中第 4 条的跳过条件；补充 ADR 0023（地图运行时由 app 懒加载）、ADR 0051（求交库不按需加载）

## 背景

现状：进入地图路由时，`withMapRuntime` 先动态导入地图运行时（maplibre-gl，gzip 268 KB），设置好 Worker 再加载地图页分块（gzip 155 KB）；创建地图时 MapLibre 再下载 Worker 脚本（gzip 142 KB），Worker 起来后才下载默认显示的省界（gzip 139 KB）。登录成功后 `await router.replace` 要等这些分块下载并执行完才跳转，所以点完登录会停一下。

阶段四定下的原则：不绑定默认的二维或三维模式，由 app 的解析函数回答进入地图时先用哪个框架；运行时按框架组织；登录页空闲时预加载预测的默认框架；用数据决定（第 8 条）。

### 实测（5E.1、5E.2，方法和全部数据见 [perf.md](../modules/perf.md)）

"点击登录 → 地图第一次加载完成"打了 User Timing 标记，两个终点是视图就绪（样式加载完成，能操作）和第一次画面稳定（视野里的瓦片、省界都已画出），以画面稳定为准。实测脚本用 Playwright 驱动 Edge，每次是新的浏览器上下文（缓存为空、新用户），CDP 限速，登录页停留 5 秒，真实后端和天地图。

基线（每档 5 次，中位数）：画面稳定在不限速 1.26 s、Fast 4G 3.33 s、Slow 4G 17.5 s。时间花在：

- 两个分块先后下载，占限速时总时间的 36%
- 视图就绪之后，最后到的是省界：它在 Worker 里下载，要等 Worker 脚本，而 Worker 脚本在创建地图时才开始下载
- 普惠体两个字重各约 5.2 MB（按授权不能子集化），限速时一直在和地图资源分带宽
- 登录页停留期间没有长任务；地图页创建、资源目录到达时各有一个 100 ms 左右的长任务

对比实验（6 份构建交替测量，每档 3 次，中位数，毫秒）：

| 构建 | 画面稳定：Fast 4G | 画面稳定：Slow 4G | 视图就绪：Fast 4G | 视图就绪：Slow 4G |
|---|---|---|---|---|
| 基线 | 3328 | 17533 | 1521 | 7021 |
| 登录页空闲时预加载运行时和地图页 | 2374（-953） | 13983（-3550） | 344（-1177） | 3496（-3525） |
| 再预热 Worker 池 | 2244（-1084） | 11797（-5736） | 347（-1174） | 4323（-2698） |
| 不预加载，两个分块同时下载 | 3193（-135） | 16065（-1468） | 1337（-183） | 5566（-1455） |
| 去掉求交库 | 3326（-2） | 17394（-138） | 1528（+7） | 6888（-132） |
| 不加载字体 | 2993（-335） | 11829（-5704） | 1245（-276） | 4692（-2329） |

不限速时各组只差几十到一百多毫秒。所有构建在登录页停留期间都没有长任务。预热 Worker 池的那一组在 Slow 4G 下视图就绪比只预加载晚 0.8 s：实验里 Worker 池在运行时加载完就预热，Worker 脚本和还在下载的地图页分块抢带宽。

其他事实：

- 所有角色登录后都进现状底图（`roleHome`），预测默认进入地图几乎不会错
- 预加载用 `import()`：模块下载后立即执行，进入路由时同一个模块直接从模块表取用
- MapLibre 的 `prewarm()` 提前建好 Worker 池（随之下载 Worker 脚本），最后一张地图移除后也不清除，直到 `clearPrewarmedResources()`
- `requestIdleCallback` Safari 不支持；`navigator.connection` 只有 Chromium 内核支持

## 候选方案

| 问题 | 候选 | 选择 |
|---|---|---|
| 要不要预加载 | 登录页空闲时预加载；登录接口返回后才开始加载（现状）；不预加载但在登录时显示加载状态 | 预加载：Fast 4G 下视图就绪从 1.5 s 到 0.34 s，画面稳定快约 1 s；不预加载时下载必然排在登录之后，加载状态只是让等待看得见 |
| 预加载什么 | 只预加载运行时；运行时和地图页分块；再加 Worker 池；再加省界 | 运行时、地图页分块和 Worker 池：前两个是视图就绪前的串行等待，Worker 池是省界的前提。省界没有实验，预取它要在 Worker 外面先请求一次、靠 HTTP 缓存，生产环境给 `/assets/*` 设长期缓存之前（阶段七）效果不确定，不做 |
| 什么时候预热 Worker 池 | 运行时加载完就预热（实验的做法）；运行时和地图页分块都加载完再预热 | 都加载完再预热：两个分块是视图就绪的前提，先让它们下完；实验里提前预热让 Slow 4G 的视图就绪晚了 0.8 s |
| 两个分块怎么下载 | 先后下载（现状）；同时下载 | 同时下载：不预加载时（已登录直接打开地图、刷新）Fast 4G 快 135 ms、Slow 4G 快 1.5 s；预加载走同一个加载函数，停留期间没下完时同样有用。页面模块执行时不创建地图，`setWorkerUrl` 只要在创建第一张地图之前即可 |
| 什么时候跳过预加载 | 省流量模式或 2G 时跳过（原则第 4 条）；只在省流量模式时跳过；从不跳过 | 只在省流量模式时跳过：登录后马上就要下载这些资源，越慢的网络预加载省得越多（Slow 4G 快 3.5 s 以上）；省流量是用户明确表示不要提前下载，照它的意思办 |
| 求交库要不要按需加载 | 选中区划时和边界一起加载；随地图页分块（现状） | 随地图页分块：去掉它 Fast 4G 只快 2 ms、Slow 4G 快 138 ms，按需加载要让区划范围多等一个模块（ADR 0051 第 1 节） |
| 默认框架怎么组织 | 现在就按框架做运行时注入（map-vue 接收各框架的加载函数）；只做最小的解析函数，注入等到第二个框架 | 最小的解析函数：现在只有二维一个使用方，注入的接口只能靠猜；路由加载和预加载都经过解析函数，三维阶段只改它和加载函数 |

## 决定

### 1. 默认框架的解析

app 里新增 `defaultMapFramework()`，回答"进入地图时先用哪个框架"，现在固定是二维（框架的类型只有 `'2d'`）。路由加载地图页、登录页预加载都按它的回答加载对应的运行时。三维阶段按原则第 1 条扩展：依据部署配置、用户配置或上次使用的框架；默认框架要登录后才知道时，登录页按上次使用的框架或部署默认值预测，猜错只多一次下载。运行时注入 map-vue 也在三维阶段有了第二个框架时再做，`withMapRuntime` 留在路由上。

### 2. 加载地图页

进入地图路由时，同时开始加载默认框架的运行时和地图页分块；两者都加载完后设置运行时（`setWorkerUrl`、`setWorkerCount`），再预热 Worker 池（`prewarm()`），然后返回页面组件。地图页之外不预热。

- 预热的 Worker 池整个会话一直保留，不调用 `clearPrewarmedResources()`：地图是首页，切到别的页面以后还会回来，重建时直接用
- 加载耗时标记的 `runtime` 步骤改为"运行时和地图页分块都加载完"

### 3. 登录页预加载

app 在进入登录页后安排一次预加载：浏览器空闲时（`requestIdleCallback`，最多等 2 秒；不支持时 `setTimeout` 1 秒）调用第 2 节的同一个加载函数，按第 1 节预测的默认框架加载运行时、地图页分块并预热 Worker 池。

- 省流量模式（`navigator.connection.saveData` 为真）时跳过；不按网络类型跳过（修正原则第 4 条）。不支持 `navigator.connection` 的浏览器按不跳过处理
- 一个页面生命周期里只安排一次；退出后回到登录页时模块已经在模块表里，不再下载
- 预加载失败时不提示、不重试，进入地图路由时照常加载（失败的原因和路由加载时一样由路由处理）
- 页面不知道预加载的存在：由 app 监听路由，登录页不依赖 app

### 4. 求交库

`@turf/intersect`（含 `polyclip-ts`、`bignumber.js`，gzip 约 15 KB）留在地图页分块里，区划范围仍是同步的（ADR 0051 第 1 节不变）。

### 5. 字体不在本 ADR 决定

不加载字体时 Slow 4G 快 5.7 s、Fast 4G 快 335 ms、不限速快 48 ms，只影响第一次访问。普惠体按授权不能子集化，能改的只有加载的时机（例如 SemiBold 等画面稳定后再加载、两个字重都推迟），这会改变第一次访问时登录页和地图页的字体显示，要在实现第 1～3 节之后，用同样的方法比较这几种时机再定，另写 ADR。

### 6. 缓存与复测

- 产物带 hash 的长期缓存、`index.html` 不缓存、开启压缩仍按原则第 7 条在阶段七做；预加载起作用的是第一次访问和每次部署后的第一次访问
- 实现后用 `--builds` 复测：实现的构建对比基线，画面稳定要不差于实验里"再预热 Worker 池"的一组（Fast 4G 约 2.2 s、Slow 4G 约 11.8 s），Slow 4G 的视图就绪要不差于只预加载的一组（约 3.5 s）
- 三维阶段 Cesium 作为第二个框架接入时，用同样的标记和脚本复测，决定另一个框架是否预加载、什么时候加载

## 后果

- 好处：Fast 4G 下登录后约 0.35 s 就看到地图（原来 1.5 s），画面稳定快约 1 s；慢网络省得更多；已登录直接打开地图时也快一些（两个分块同时下载）
- 好处：路由加载和预加载共用一个加载函数，三维阶段只改解析函数和加载函数
- 代价：登录页额外下载约 580 KB（gzip：maplibre-gl 268 KB、地图页分块 154 KB、Worker 脚本 142 KB、样式表 16 KB），打开登录页却不登录的人白下载；Worker 池整个会话常驻（4 个 Worker 的内存）
- 代价：地图页分块里所有模块在登录页上执行；实测没有长任务，以后地图页分块的模块在顶层做了重的计算会落到登录页上
- 风险：两个分块同时加载后，样式表插入的顺序要和原来一致（maplibre-gl 的 CSS 在前），实现时在真实页面上核对
