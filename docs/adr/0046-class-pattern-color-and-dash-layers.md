# 0046. 分类取值的纹理默认色与按线型拆层

- 状态：已接受
- 日期：2026-10-12
- 修改 ADR 0045 第 1 节（分类样式取值的纹理颜色默认值）、第 2 节（一个面资源最多三个图层改为六个）；补充 ADR 0044、0045 的线型推导（线型不同的要素分到不同图层）

## 背景

5C.5c-3 用真实数据验收时（2026-10-12，开发服务器 + 真实后端）发现两个问题。

### 分类样式选了花纹看不见

ADR 0045 第 1 节规定纹理颜色默认是主色。统一样式的填充是 0.35 透明度，同色花纹叠在上面看得见；分类样式的填充是取值颜色、不透明，选了花纹后同色叠同色：地类图斑的水田选斜线，地图上没有任何变化，编辑器下拉框里 8 种花纹的预览也都和均匀填充一样。要看到花纹，必须再手动改纹理颜色。

旧项目也是这样（`resourceSymbolModel.js` 中 `symbol.patternColor = item.color`），它的花纹选项用白色线条画在固定底色上，不反映实际效果，所以不显眼。

分类样式的颜色都写在本地配置里（`style-registry.ts`、`landuse.ts`）：面的分类是地类和城镇村类型，共 47 种颜色，Lab 亮度在 54～94 之间（中位数 76），都是浅色或中等亮度；另外两个分类（水域线、农村道路）是线，没有纹理。

### 线型从全实线改成逐项不同时 MapLibre 报错

分类样式里所有取值都是实线时，推导不设 `line-dasharray`；把其中一项改成虚线后，属性变成按取值 `match`（实线写 `[1, 0]`）。这一刻控制台报 4 次 `Cannot read properties of undefined (reading '0')`，几帧后自行恢复。

原因在 MapLibre 6.12（2026-10-12 读源码，上游 main 分支未修复）：

- 改成按要素取值后，MapLibre 让数据源重新解析瓦片；新瓦片回来之前，继续用旧瓦片的缓冲区和绑定器画新样式
- 旧瓦片里 `line-dasharray` 的绑定器是常量绑定器（`CrossFadedConstantBinder`）。它在构造时把 `patternFrom/To` 设为 `null`（`setUniform` 遇到 `null` 跳过），却没有初始化 `dashFrom/To`；这两个值只在图层的线型是常量时、每次绘制前写入
- 之前不设线型时它们从没写入过，新样式下按要素取值又不写，于是 `setUniform` 读到 `undefined`

浏览器测试复现（真实 MapLibre、内联 GeoJSON）：

- 不设线型 → `match`：报 4 次；常量数组 → `match`：不报错（绑定器里留着上次写入的值）；`match` → 常量、不设：不报错
- 同一个图层在常量之间切换（不设 → `[3, 2]` → `[1, 2]` → 不设）：不报错，不重新解析瓦片，下一帧就画出新线型
- 删掉一个图层、加上换了线型的新图层：新图层要等瓦片重新解析，2 万条线时第 4 帧才画出来，中间这个资源是空白的

影响：抛错发生在每帧的绘制中途，那几帧画到这个图层就停下，上面的图层（注记、行政区界线、其他资源）短暂缺失（按源码推断）；会话状态、视图状态（不会进入 `failed`）、保存的偏好都不受影响。触发场景是分类的线资源第一次改某个取值的线型，以及面的描边图层已经存在、全是实线时改某项的线型。Vitest 浏览器模式会把未捕获的错误算作失败，按现在的推导写这个交互的浏览器测试会失败；新方案的测试不屏蔽异常，有未捕获的错误就失败。

### `[1, 0]` 和原生实线不等价

审阅时的实测（真实浏览器，DPR 1，白底黑线）：`[1, 0]` 走虚线着色器，1 像素圆头实线同一位置的灰度从 128 变成 147，0.6 像素时差别更大；0.6 像素正是 M 档线宽在低缩放下的宽度。所以"实线也写 `[1, 0]`"会让默认的概览变浅；现在分类样式里实线和虚线混用时，实线已经是 `[1, 0]`，比全实线时浅。

## 候选方案

| 问题 | 候选 | 选择 |
|---|---|---|
| 分类取值的纹理默认色 | 保持主色（同旧项目），只把下拉框的预览改成中性色画形状；取值颜色加深；按亮度加深或提亮 | 加深：选了花纹立刻看得见，下拉框的预览如实反映效果。面的分类颜色都不深，加深就够；以后新增很深的分类颜色时再考虑提亮 |
| 加深的算法 | RGB 各分量按比例变小；HSL 降低亮度；Lab 空间往黑色插值 | Lab 插值：感知上均匀，各种色相加深的程度一致；用 style-spec 的 `interpolates.color`，不加依赖。它也插值透明度（直接以 `Color.black` 为终点时 0.35 会变成 0.61），所以终点用和输入同透明度的黑色 |
| 线型报错 | 给 MapLibre 打补丁（`setUniform` 里 `!== null` 改成 `!= null`，实验有效）；实线也写 `[1, 0]`；按线型拆成多个图层，每层的线型是常量；不修 | 按线型拆层：不动依赖；图层的线型永远是常量，不经过"常量绑定器 → 按要素取值"，瓦片加载途中切换也不会报错；实线保持原生绘制，顺带修好混用时实线变浅。补丁要随每次升级重做；`[1, 0]` 让默认概览变浅 |
| 拆层后的图层 ID | 每种线型固定一个 ID（实线是主图层，其余加后缀）；主图层放用到的线型里最靠前的一种，其余各加后缀 | 后者：只用一种线型时（统一样式改线型最常见）只是主图层在常量之间切换，立刻生效、不空白；固定 ID 时要删旧加新，中间空白几帧。主图层总在，和面的主图层一致 |

## 决定

### 1. 分类取值的纹理默认色

- 分类样式里每个取值的纹理颜色默认是取值颜色在 Lab 空间往黑色插值 0.4：`interpolates.color(color, new Color(0, 0, 0, color.a), 0.4, 'lab')`，透明度不变；比例在验收时用真实数据确认
- 统一样式不变，纹理颜色默认仍是主色
- 默认值不保存（ADR 0044 只记差异），存储格式、版本不变；用户改过的纹理颜色照旧；之前保存了花纹、没改纹理颜色的取值，刷新后自动变成加深色（之前本来就看不见花纹）

### 2. 按线型拆层

线资源的线图层、面的描边图层都按线型拆分：

| 图层 | ID | 内容 |
|---|---|---|
| 主图层 | 线：`resources-<code>`；面的描边：`resources-<code>-outline` | 用到的线型里最靠前的一种（顺序：实线、虚线、点线、点划线） |
| 其他线型 | 主图层 ID 加 `-dashed`、`-dotted`、`-dash-dot` | 其余用到的线型各一层 |

- 只建实际用到的线型；每层的 `line-dasharray` 是常量：实线不设，虚线 `[3, 2]`，点线 `[1, 2]`，点划线 `[4, 2, 1, 2]`；颜色、线宽、偏移等仍按取值推导
- 只有一种线型时只有主图层，不加线型的过滤；有多种时，每层在原有过滤（几何类型等）之外加上 `['==', 要素的线型, 本层的线型]`：要素的线型直接用 `classExpression` 推导（输出取值的线型名），和颜色共用同一套匹配规则和优先级（地类先按编码、编码没命中才按名称找历史地类），兜底取值也由它给出，所以每个要素恰好进一层；不另写按编码、按名称的过滤
- 从下到上按线型的顺序叠放；同一资源的要素按线型分组绘制，不再按数据顺序（同一资源的线很少交叠，面的描边内收、不交叠）
- 线资源最多四个图层；面资源最多六个（主图层、纹理图层、四个描边图层）；透明度乘在每个图层上，数据源仍只有一个
- 切换时：主图层只在常量之间换线型、换过滤；新增的线型层要等瓦片重新解析，在此之前离开主图层的要素仍按旧瓦片画；去掉一个线型层时，回到主图层的要素在重新解析完成前短暂不显示
- 其他拥有者的 line 图层也不让 `line-dasharray` 在常量和按要素取值之间切换（写进 AGENTS.md）

### 3. 验收

- 纹理：地类图斑各取值选花纹后立刻看得见，下拉框的预览和地图一致；加深的比例在浅色（水浇地、旱地）和中等亮度（林地、城镇）上都可辨识；用户改过的纹理颜色不变
- 线型：四种线型的分配正确，来回切换（全实线 → 部分取值虚线 → 多种线型 → 全实线、统一样式与分类样式互换）控制台没有错误；兜底取值不丢失、不重复；编码命中、名称指向另一个历史地类的要素只进编码对应取值的线型层；实线外观和改动前一致（细线、低缩放对比截图）
- 性能：全省视图和 12 级以上的地类图斑，多个描边线型层时的加载和拖动用真实 MVT 实测
- 单元测试：用 style-spec 对各层的过滤条件求值，每个要素恰好通过一层，包括兜底取值和"编码命中、名称指向另一个历史地类"的要素
- 浏览器测试：用推导出的图层和内联 GeoJSON，线型来回切换时没有未捕获的错误，要素进入对应的线型层（把拆层改回一层 `match`，测试要失败）

## 后果

- 好处：分类样式选了花纹就看得见；线型切换不再报错，浏览器测试可以覆盖这个交互；实线始终原生绘制
- 代价：用了多种线型的资源多出图层，每个要素多一次过滤计算、每块瓦片多几次绘制调用；只用一种线型时没有变化
- 代价：一个资源的图层更多（面最多六个），推导要处理线型的分组、过滤和兜底
- 代价：分类取值的纹理默认色和统一样式不同（一个加深、一个用主色），文档和编辑器的说明要写清楚
