# 0154. 发布的默认符号：把某个人调好的图例样式作为默认

- 状态：已接受
- 日期：2026-11-11
- 补充：ADR 0044 第 2 节（默认符号由登记表给出，现在再叠加一份发布的默认符号）
- 修改：ADR 0123 第 3 节（用户没选过样式方式时的推导，以及什么时候记下选的方式）

## 背景

用户 2026-11-11 提出：有人在自己的浏览器里把资源图层的符号（图例样式）调好了，要把这些样式作为项目的默认样式，并且不能改动别人自己调过的样式。

现状（2026-11-11 核对代码）：

- 用户调的符号是叠加在默认符号上的覆盖，只记和当时默认不同的字段（ADR 0044 第 3 节）。拥有者 `useResourceSymbols` 按 ADR 0042 保存：名称 `resource-symbols`，版本 1，存在 IndexedDB 的 `yzt-preferences` 库、`preferences` 仓库，键是 `encodeURIComponent(登录名)/resource-symbols`，值是 `{ version, value }`
- `usePreference` 读到版本不同或通不过 schema 的数据，就当作没有存过；之后用户改动任何符号，这条数据会被当前状态整体覆盖。所以改版本号、把 `storedSymbolsSchema` 改得更严，都等于清掉所有人的自定义
- 默认符号大多是算出来的：统一样式按资源在目录里的顺序从配色板取色，分类样式取字典的颜色（ADR 0044 第 2 节、ADR 0123）
- 资源目录来自后端，仓库里只有按属性配色的资源登记在 `style-registry.ts`，只有统一样式的资源不在仓库里
- idb-keyval 打开数据库时不指定版本，只在第一次建库时建仓库（`shared/storage/idb-store.ts`）。在没有这个库的浏览器上调用 `indexedDB.open('yzt-preferences')` 会建一个没有仓库的空库，之后应用就存不了任何偏好

## 候选方案

| 问题 | 候选 | 选择与理由 |
|---|---|---|
| 新默认放在哪 | 改 `style-registry.ts` 的代码；feature 里的数据文件，叠加在算出的默认符号上；发布目录里的运行时文件；直接写进每个用户的偏好 | 数据文件：默认符号多是算出来的，写进代码要另加一套覆盖的结构，工具还要改写源码；数据文件的格式和用户存的覆盖一样，导出的数据几乎原样搬过来，评审看 JSON 的差异。运行时文件不用重新构建，但页面要先读到它才能确定默认符号、恢复覆盖也要等它，多一个加载状态，而这次的要求是写进代码。写进每个用户的偏好就是在改别人的数据 |
| 样式方式要不要一起带上 | 只带符号的字段；连样式方式一起带上 | 一起带上（用户 2026-11-11 确定）：调好的人可能把某个按属性配色的资源换成了统一样式，只带字段时别人看到的和他看到的不一样 |
| 用户没选过方式时怎样推导 | 选过的、调过统一样式的按统一样式，其余用默认方式；再加一条：只调过取值的按分类样式 | 加一条：默认方式改成统一样式后，只调过取值、没碰过切换的用户不会被切到统一样式、看不到自己调的取值。默认方式是分类样式时，这条和原来的规则逐条相同 |
| 导出的方式 | 页面上加导出按钮；控制台粘贴的片段 | 片段：只在偶尔换默认时用，不值得做界面；不依赖应用的代码，生产构建上也能用 |
| 导入工具怎样拿到页面的 schema 和登记表 | 在工具里另写一份；Node 直接导入应用的模块；逻辑写在 feature 里，命令行用 Vite 加载 | 用 Vite 加载：应用的模块导入时不写扩展名、用 `@/` 别名，Node 直接加载不了；另写一份迟早和页面不一致。命令行的类型只读一个不导入别的模块的约定文件 |
| 导入工具默认做什么 | 直接写入，用 git 还原；只打印差异，加参数才写入 | 只打印差异，`--write` 才写入：先看清楚改了哪些资源再落盘 |

## 决定

### 1. 三层

推导用的符号 = 代码算出的默认符号 → 发布的默认符号 → 用户的覆盖（拖动取色时再叠加预览）。

- 发布的默认符号在 `features/resource-map/resource-symbol-defaults.json`，格式就是 `storedSymbolsSchema` 的值（按资源记统一样式、样式方式、各取值，只记和代码算出的默认不同的字段）。`style-registry.ts` 加载时用同一个 schema 校验，合进 `resourceStyle(code)` 的 `symbols`
- `defaultSymbol`、`classDefaultSymbol` 叠加它，图层、图例、符号编辑器、开发页都从这两个函数取默认，一处生效
- 用户的覆盖照旧只记和默认不同的字段，比较的是叠加之后的默认；"恢复默认"恢复到发布的默认符号；"已自定义"、"全部恢复默认"只看用户自己的覆盖

### 2. 样式方式

- 一层覆盖决定的方式（`layerMode`）：选过的方式；没选过时调过统一样式的是统一样式，只调过取值的是分类样式；都没调过时由下面一层决定。发布的默认符号这一层的下面是分类样式，用户这一层的下面是发布的默认方式
- 整理覆盖（`pruneOverride`）时，选的方式和默认方式相同、由调过的内容也推得出时才不记，其余都记下。默认方式是分类样式时，和 ADR 0123 第 3 节的存法相同；默认方式是统一样式时，选分类样式要记下来，否则下次打开又变回统一样式。整理要知道资源的默认方式，拥有者在保存、恢复、预览时都传进去

### 3. 导出：控制台片段

`features/resource-map/symbol-defaults/export-snippet.js`，在部署的页面上打开开发者工具，把整个文件粘贴到控制台运行：

- 先用 `indexedDB.databases()` 确认库存在，不存在时不调用 `open`；`open` 时如果触发建库，在 `upgradeneeded` 里中止，不留下空库
- 只开只读事务，读出所有以 `/resource-symbols` 结尾的键（这个浏览器上登录过的每个账号一条），原样下载成 `resource-symbols-<日期>.json`；没有时报出原因
- 这是唯一绕过 `shared/storage` 读偏好的代码：它在应用之外运行。数据库名、仓库名、键的写法和应用一致，由浏览器测试核对

### 4. 导入：`pnpm --filter yzt symbols:import`

- 用页面同一个 schema 校验，版本必须是 1；文件里有几个账号时用 `--login` 选
- 选中资源的新默认 = 现在的发布默认叠加这个人的覆盖，也就是他在页面上看到的样子；前提是他用的部署和仓库里的默认文件一致。样式方式按他看到的写
- 按属性配色的资源，取值不在规则里的跳过；没登记分类的资源带了取值或样式方式时跳过这些部分；没登记分类的资源离线确认不了还在不在目录里，列出来让人核对
- 打印"资源 / 取值 / 字段：旧 → 新"的差异，`--only` 只导入部分资源，`--write` 才写入；文件按 code、取值排序，字段按点、线、面的顺序
- 合并、校验、差异在 `features/resource-map/symbol-defaults/import.ts`，页面不导入；命令行 `tools/symbol-defaults/cli.ts` 用 Vite 的 `runnerImport` 加载它
- 导出的文件含登录名，只放在 `local/symbol-defaults/`，不提交

### 5. 不改动别人的自定义

- 不改偏好的版本号，`storedSymbolsSchema` 不变；以前存下的覆盖照样读出，叠加在新的默认上
- 改动只在于"默认"本身：用户没改过的字段、没选过的样式方式跟着新的默认变，这是 ADR 0044 选择"只记差异"时就定下的（默认调整时没改过的字段跟着变）

### 6. 测试

- 发布的默认符号是导入的数据，随时会换：`src/test-setup.ts` 把它换成空的，其他测试都按代码算出的默认符号；叠加和样式方式由 `symbol-defaults.test.ts` 用自己的一份数据测，仓库里的文件由 `symbol-defaults/import.test.ts` 读原文检查（通过 schema、取值在规则里、是工具写出的固定格式）
- 片段用浏览器测试，在真实的 IndexedDB 上验证读出的内容、只开只读事务、库不存在时不打开也不新建

## 后果

- 好处：换默认样式只是一份 JSON 的改动，评审看得清；别人存下的覆盖不受影响，调过的字段保持原样
- 好处：默认方式没改成统一样式时，样式方式的推导和存法与原来逐条相同
- 代价：调好的人如果用的是旧部署（发布的默认符号和仓库里的不同），导入的结果是两者的混合；文档写明先确认部署和仓库一致
- 代价：只有统一样式的资源离线核对不了，要人对照页面上的图层确认
- 代价：用户没改过的字段会跟着新的默认变，有人可能觉得"自己的样式变了"；这正是要的效果，发布时说明
