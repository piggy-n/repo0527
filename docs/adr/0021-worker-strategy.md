# 0021. Worker 策略：二维不自建渲染 Worker，统一通信层与瓦片数据服务

- 状态：已接受
- 日期：2026-10-09

## 背景

旧项目（yzt `master-demo` 836f03b）的三维用了两种 Worker：矢量瓦片的下载、解码和栅格化（旧注释：放进 Worker 之前，一次 z12 跳转在主线程上花约 12.8 秒），以及漫游用的导航网格。消息靠 `type` 字符串区分，没有类型；Worker 池的状态是模块变量，不属于任何实例。

阶段四讨论时提出的问题：二维如果也采用类似的 Worker 方案，实际收益有多大，是否值得在架构层统一考虑。

MapLibre 本身已经在自己的 Worker 池里下载和解码矢量瓦片、切分 GeoJSON、构建渲染数据，默认最多 3 个 Worker。留在主线程的是标注碰撞检测、GPU 上传和 `queryRenderedFeatures`，这些无法由我们替换。旧项目二维部分记录过的主线程问题：

| 问题 | 旧注释里的实测 | 性质 |
|---|---|---|
| 图例统计"当前出现了哪些地类"，对整屏做 `queryRenderedFeatures` | 全省视图约 20 万个要素，阻塞主线程近 1 秒 | 计算热点 |
| 大瓦片加载期间，每次数据源加载完成就扫描一遍 | 单次 1～2 秒 | 时机问题，旧代码已改为空闲时扫描 |
| 测量结束、鼠标不动时，两个测量数据源仍每秒 `setData` 60 次 | — | 写法问题 |
| 每一帧都打 `console.log` | — | 写法问题 |
| mapbox-gl 的 Worker 从 2 个加到 4～6 个 | z10、z12 快 20%～28% | 引擎自己的 Worker 不够用 |

## 候选方案

1. 二维也自建 Worker，把能移的计算都移出主线程
2. 二维不自建渲染 Worker；只把实测确认的热点移出主线程；统一的是"怎么写 Worker"和"瓦片数据怎么处理"

## 决定

选方案 2。

1. **二维不自建渲染 Worker。** 渲染管线在 MapLibre 内部，能调整的是它的 Worker 数量（`setWorkerCount`，接入地类图斑时实测，ADR 0019）和每张瓦片的工作量（例如旧注释记录：透明的纹理伴随图层会让 Worker 为每张瓦片多构建一份面几何）
2. **主线程热点先实测，再决定怎么移。** 目前确认的只有图例统计。阶段五用真实数据测出 MapLibre 6 的耗时后，在三种做法中选：后端按范围聚合；自己的 Worker 只解码瓦片属性、按瓦片缓存后合并；沿用旧做法，只在需要时统计。时机和写法问题不需要 Worker：在 ADR 0020 的结构里，只有会话状态真正变化时才写地图
3. **统一的 Worker 通信层**，所有自建 Worker 都用它：
   - 每个 Worker 的协议用一张"请求类型 → 响应类型"的表描述，调用方的参数和返回值类型由表推断；消息本身是可辨识联合
   - 请求和响应按 ID 配对；用 `AbortSignal` 取消，取消时向 Worker 发一条取消消息
   - 支持转移所有权的数据（transfer），错误序列化后传回调用方
   - Worker 池归某个实例所有，随拥有者释放，可以延迟终止（旧项目在最后一个使用方注销 30 秒后终止，避免来回切换时丢缓存）
   - 手写实现，不引入 comlink：有类型的消息协议是阶段四的学习点
   - 与地图无关，放在 `libs/utils`（`@yzt/utils`）
   - 测试不需要真的 Worker：通信层只依赖 `postMessage` / `message` 事件，测试中用 `MessageChannel` 的两端代替主线程和 Worker。已实测：Vitest 的 jsdom 环境里有 `MessageChannel`，能往返收发、转移 `ArrayBuffer`；这个环境里没有 `Worker`
4. **瓦片数据服务独立于引擎**，放在 map-core：下载去重、解码、属性裁剪、按字节预算淘汰缓存、同一张父瓦片固定交给同一个 Worker，算法来自旧项目的三维 Worker 池，从三维栅格化里拆出来。命中缓存时调整顺序，使它成为真正的 LRU（旧代码命中时不调整，实际是先进先出）。使用方：
   - 三维的瓦片栅格化和标注
   - 二维的图例统计（如果第 2 条的实测选了 Worker）
   - 以后的三维点选：直接在已解码的瓦片上做命中检测，不再先对齐二维（ADR 0020）

   和 MapLibre 之间避免重复下载的做法（依靠 HTTP 缓存，或用 MapLibre 的 `addProtocol` 把它已下载的数据复制一份），实现时决定
5. **同一套样式语义**：Worker 里的表达式和过滤条件用 `@maplibre/maplibre-gl-style-spec` 求值，与二维完全一致，不再手写求值器

## 后果

- 好处：二维不增加没有收益的复杂度；所有 Worker 的写法、取消、释放方式一致，消息有类型检查
- 好处：瓦片数据服务独立后，三维点选可以摆脱对二维的依赖，服务于 ADR 0020 的无感切换
- 代价：通信层要在出现真实使用方之前先做出来（阶段四），有过度设计的风险。所以只实现上面列出的能力，用测试约束接口，第一个真实使用方出现时再调整
- 待定：Worker 入口文件要按 `WebWorker` 环境做类型检查，不能和 DOM 环境放在同一份 tsconfig 里（ADR 0018），出现第一个 Worker 入口时确定配置
- 待定：`utils` 目前还不存在，通信层是它的第一个模块；地图链拆包时它随之一起拆（ADR 0018）
