# 0027. 地图能力的分层与页面组装

- 状态：已接受
- 日期：2026-10-09

## 背景

阶段五要迁移现状底图，并且先建设公共地图能力，再由各地图页面按需组装（[roadmap.md](../roadmap.md)"阶段五"）。旧项目（yzt `master-demo` 836f03b）里，地图能力在各页面的分布：

| 能力 | 现状底图 | 数据查询（4 页） | 指标 | AI 对话 |
|---|---|---|---|---|
| 天地图底图 | ✓ | ✓ | ✓（可勾选） | ✓ |
| 省市县边界 | ✓（控制栏） | 另写了 `TiandituBoundaryLayer` | ✓（基础图层勾选） | ✓（省界） |
| 定位时避开悬浮面板 | — | 自己算 padding | 自己算 padding | — |
| 绘制（框选、多边形） | 点选里的框选 | 另写了 `SpaceQueryDrawingManager` | — | — |
| 工具栏（默认视角、点选、测距、测面、区划定位、坐标定位） | ✓ | 关掉 | 关掉 | 关掉 |

旧项目做过"公共地图"：`CommonMap` → `MapContainer` → `MapService`，用一组开关（`showToolbar`、`enableManagedLayers`、`enableUnifiedFeatureSelection`、`enableAiResults` 等）区分页面。结果是：

- 开关越来越多，所有能力都要初始化，开关又把代码分成新旧两套路径
- 页面要的能力开关里没有时，只能绕过它：上面的边界、绘制、定位各页面又写了一份，数据查询页还直接导入 `mapbox-gl`
- 页面调用地图能力要经过三层 `defineExpose` 转发 20 多个方法

已有的约束：

- AGENTS.md 预留了 `libs/map-vue`，lint 只允许它依赖 `@yzt/utils`、`@yzt/map-core`，并且只能动态 `import()` map-cesium
- libs 不读 env、store、router 和全局单例（ADR 0004）；`libs/ui` 不能引用 `SvgIcon`（ADR 0016）
- 只有 `libs/map-core/maplibre/` 和 `app/` 能导入 maplibre-gl（ADR 0024）
- 地图会话是二三维共同的唯一真相源，拥有者从自己的状态推导分组（ADR 0020、0022）

## 候选方案

1. **带开关的公共地图组件**（旧做法）：一个组件包下所有能力，页面传配置
2. **每个页面自己写**（旧项目其他页面的现状）：互不影响，但同样的能力写很多份
3. **分层的积木**：与框架无关的逻辑在 libs，项目配置和界面在 `shared/map`，业务数据驱动的部分在 features，页面挑选组合

map-vue 的位置另有两种选择：`libs/map-vue`（不含项目配置），或 `shared/map-vue`（可以直接读 `appConfig`、用 Element）。

## 决定

采用方案 3，map-vue 放在 `libs/map-vue`。

### 1. 五层的职责

| 层 | 放什么 | 不放什么 |
|---|---|---|
| `libs/map-core` | 地图会话（样式、相机，以后的当前工具与选择）、视图接口与 MapLibre 适配器；与框架无关的工具逻辑（工具状态、测量计算） | Vue、项目配置 |
| `libs/map-vue` | 地图与 Vue 的衔接：会话的提供与注入、地图画布组件、把推导出的分组提交给会话、把会话和视图的事件桥接成 Vue 的状态（ADR 0028） | Element、Pinia、Vue Router、项目配置；除画布容器外不渲染界面 |
| `shared/map` | 项目级的公共地图能力：地图的默认相机和范围、底图目录与底图的拥有者、行政区边界、工具栏和各种地图控件的界面、视图失败时的提示 | 业务接口驱动的图层 |
| `features/*` | 业务数据驱动的拥有者和界面：资源图层（接口、规范化、显示状态、拥有者）、图层面板、图例、点选详情 | 其他 feature 的东西 |
| `pages/*` | 画布布局；声明分组顺序；挑选公共能力和 feature，把它们的推导函数绑定到分组 | 地图逻辑 |

`shared/map` 需要读 `appConfig`（如天地图的 key）、用 Element 和 `SvgIcon`，所以不能放进 libs。它是"项目的公共地图能力"，map-vue 是"任何 Vue 项目都能用的衔接"。

### 2. 用组合，不用开关

每项能力由两部分组成：逻辑（拥有者或工具）和可选的界面。页面挑选需要的部分，地图上就只有这些部分，不做带开关的全能地图组件。

| 能力 | 逻辑 | 界面 | 页面做什么 |
|---|---|---|---|
| 底图切换 | `shared/map` 的底图拥有者：底图选择 → 分组 | `shared/map` 的底图面板 | 绑定底图分组，决定放不放面板 |
| 测距 | map-core 的测距工具，map-vue 衔接 | `shared/map` 的工具栏按钮 | 绑定测量分组，挑选按钮 |
| 资源图层 | feature 的拥有者：图层树与显示状态 → 分组 | feature 的图层面板、图例 | 绑定资源分组，放置面板 |

### 3. 样式只由页面绑定

- 页面创建会话时声明全部分组和它们的顺序（ADR 0022）
- 拥有者不提交样式，只给出推导函数；页面在一处把推导函数绑定到分组，同一轮变化的分组一次提交，跨分组的引用（如高亮引用资源分组的数据源）因此是原子的（写法和失败语义见 ADR 0028）
- 一个分组只能绑定一次，重复绑定直接抛错，不让两个拥有者互相覆盖
- 通过注入拿到地图上下文的组件不能写样式，只能读相机、视图和视图状态
- 拥有者的数据源和图层 ID 以分组名为前缀：不同分组之间 ID 重复时，会话会拒绝整次提交（ADR 0022），前缀从命名上避免冲突。引用别的分组的数据源时，用被引用方提供的 ID（例如资源拥有者给出的数据源 ID），不自己拼

### 4. 同一时间只有一个激活的工具

测距、测面、点选、绘制抢同一套指针输入。公共工具和页面专属的工具（例如数据查询的空间绘制）注册进会话里同一个工具模型，切换时旧工具退出、新工具激活，不再靠互相询问"能不能用鼠标"（旧代码的 `isInteractionBlocked`）。工具模型和视图的输入、拾取、投影在 5B.3 实现。

### 5. 依赖规则

- map-vue 不依赖 element-plus、`@element-plus/**`、pinia、vue-router，由 lint 强制（在现有"libs 不依赖 vue 等"的规则之外，单独为 map-vue 加一条）
- `shared/map` 通过 `@yzt/map-vue`、`@yzt/map-core` 使用 libs，可以使用 Element、`SvgIcon`、`appConfig`
- 放在哪一层看它是否属于某个业务域，不看有几个使用方：多个页面需要同一项业务能力（如资源图层）时，各页面组合同一个 feature，业务图层、接口和规范化逻辑留在 feature 里；只有脱离具体业务域的通用部分（不依赖业务接口和业务数据结构）才放进 `shared/map`
- features 之间不互相导入；一个 feature 要用另一个 feature 的结果时，由页面把两者组合起来（例如把 A 的状态或推导函数作为参数传给 B）
- 依然只有 `libs/map-core/maplibre/` 和 `app/` 能导入 maplibre-gl

### 6. 公共能力的接口只做现有使用方需要的

现状底图是第一个使用方，接口只做它需要的部分；第二个使用方出现时（例如阶段六数据查询的空间绘制），再按它的需要扩展，不为想象中的使用方预先设计。页面专属的需求先写在页面或所属的 feature 里；其中脱离业务的通用部分在有第二个使用方时，再抽到 `shared/map` 或 libs（按第 5 条判断放哪一层）。

### 7. 地图运行时暂不改动

maplibre-gl 的 `setWorkerUrl` 和 CSS 仍由路由的 `withMapRuntime` 在进入地图页之前加载（ADR 0023）。运行时按框架组织、由 app 注入给 map-vue 的做法，在 5D 实测加载策略后再定。

## 后果

- 好处：页面上只有它挑选的能力；同一项能力只写一次；逻辑在 libs，二三维、各页面共用；样式只在页面的一处绑定，哪个分组来自哪个拥有者一目了然
- 好处：map-vue 不含项目配置，map-cesium 拆包时可以一起拆出去（ADR 0018）
- 代价：一项能力要分在两三层里写（逻辑、衔接、界面），比写在一个组件里多几个文件；页面的装配代码比传一个配置对象长
- 代价：现在只有一个使用方，公共接口仍可能在第二个使用方出现时调整
- 待定：画布型布局里"被悬浮面板占用的区域"怎样交给定位使用（5A.3）；工具模型的接口（5B.3）
