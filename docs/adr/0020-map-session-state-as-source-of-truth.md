# 0020. 二三维关系：地图会话状态是唯一的真相源

- 状态：已接受（第 1 条中选择状态的范围由 0022 修正；"候选方案"中对方案 B 的比较由 0024 修正）
- 日期：2026-10-09

## 背景

现状底图有二维（MapLibre）和三维（Cesium）两个框架，用户可以随时切换。旧项目（yzt `master-demo` 836f03b）的做法是"二维是唯一真相源，三维是它的一面镜子"（分析见 [modules/map-core.md](../modules/map-core.md)"二维与三维的关系"）：

- 二维地图一直存活。三维监听它的 `styledata`，每次取整份样式对比后重建镜像。二维加载瓦片时，5 秒内会触发 300 多次 `styledata`，只能用防抖加最长等待压住
- `CesiumEngine` 没有实现 `IMapEngine`，是另一套接口。注释里"接入 Cesium 只需新增一个引擎实现"的设想没有落地
- 二维还充当三维的查询后端：三维点选要先把二维相机对齐过去，等它加载完（最多 900ms）再查询。不让二维时刻跟随三维相机，是因为代价太大（旧注释：一次跳转主线程最高占 9.2 秒）
- 有几处补丁：三维期间替换 `map.setLayoutProperty` 压住标注图层；测量时把透明的二维画布叠到三维上面接管鼠标；三维用手写的表达式求值器，只覆盖部分算子

镜像的收益很大：图层、图例、区划裁剪、高亮、测量和绘制结果，在三维里都不用再写一遍。旧项目已经基本做到切换后状态不丢，这次重构要把它作为**核心能力**：无论当前以哪个框架为主，用户在一个框架里的操作和状态，切换到另一个框架时都尽量保留，不需要重新操作，做到接近无感切换。只能由某个框架实现的功能（三维漫游、3D Tiles 等）保持独有，不强行统一。

## 候选方案

| | A. 沿用：活着的二维地图是真相源 | B. 自定义的引擎无关模型，两个框架都是适配器 | C. map-core 持有状态，两个框架都订阅它 |
|---|---|---|---|
| 功能只写一次 | 是 | 否：点选、测量、绘制、高亮、区划裁剪在 Cesium 里各写一遍 | 是 |
| 图层用什么描述 | MapLibre 样式规范 | 自己设计，要能表达 `interpolate`、`match` 等表达式，等于重新发明样式规范 | MapLibre 样式规范 |
| 三维怎么知道变化 | 监听 `styledata`，取整份样式对比 | 各自调用 | 状态发出细粒度的事件 |
| 视图上的差异（例如三维期间不画二维标注） | 猴子补丁 | 各自处理 | 适配器层面的覆盖，不改状态 |
| Manager 的测试 | 需要假引擎 | 需要假引擎 | 断言状态即可，不需要 WebGL |
| 二维必须存活 | 结构上必须 | 不需要 | 结构上不需要 |

## 决定

选方案 C，并把真相源从样式扩大到整个地图会话。

### 1. 地图会话状态

map-core 持有**地图会话状态**，是二维和三维共同的唯一真相源：

| 组成 | 内容 |
|---|---|
| 样式模型 | 数据源和图层，用 MapLibre 样式规范的类型描述：勾选、透明度、排序、图例配色、符号、年份、区划裁剪；覆盖物（边界、高亮、测量结果、绘制结果）也是其中的 GeoJSON 数据源和图层 |
| 相机 | 二三维共用的 `CameraState` |
| 当前工具 | 浏览、点选、框选、测距、测面、绘制 |
| 选择状态 | 选中的要素、候选列表、详情 |

- 会话状态是纯 TS，修改后发出带类型的事件，不依赖 Vue 和任何引擎。阶段五由 map-vue 把它桥接成 Vue 的响应式状态
- Manager 修改会话状态，不直接写引擎
- 样式模型的实现方式（可变存储加细粒度事件，或不可变快照加 style-spec 的 `diff`）在设计接口时确定。高频更新（例如测量时跟随鼠标的橡皮筋）不能走整份样式对比

### 2. 两个框架都是会话状态的读者

- **MapLibre 适配器是唯一写二维地图的地方**：订阅会话状态，把变化写进地图。其他代码只能通过它读（查询、投影、指针事件），不能直接修改地图。这样 MapLibre 内部的那份样式才能和样式模型保持一致
- **Cesium（map-cesium）是另一个读者**：镜像样式模型、同步相机、提供自己的指针事件和查询实现。它不实现二维的引擎接口，因此不需要引擎工厂
- 视图上的差异由适配器自己决定，不改会话状态。例如三维期间二维不画标注：样式模型里仍是"显示"，二维适配器暂时不画，切回后按模型恢复
- 三维里的样式表达式和过滤条件用 `@maplibre/maplibre-gl-style-spec` 求值，与二维语义一致（ADR 0019、0021）

### 3. 状态分三类

| 类别 | 内容 | 切换框架时 |
|---|---|---|
| 共享状态 | 上面的地图会话状态 | 两个框架都表现出来 |
| 框架独有状态 | 三维：漫游、3D Tiles 与白膜的显示和效果、钻地、地表透明度；二维目前没有 | 由各自的模块保管（例如 map-cesium），切走时隐藏但保留，切回时恢复 |
| 引擎内部状态 | 瓦片、缓存、GPU 资源 | 不保留，可以重建 |

### 4. 独有功能按能力声明

每个框架声明自己支持的能力（例如 `roam`、`tileset3d`）。界面先查询能力，再决定按钮可用、提示还是隐藏；不支持时不强行统一。三维第一次加载后保持挂载，切回时独有状态还在。

### 5. 相机：表达不了时降级，切回时还原

三维相机可能处在二维表达不了的状态（钻地、俯角超过 MapLibre 的上限、在车站里漫游）。切到二维时，相机收到最接近的合法值；切回三维时，如果期间二维相机没有变过，就还原离开时三维的精确相机，而不是从降级后的值反推。

### 6. 交互工具不绑定具体引擎

- 工具同一时间只有一个处于激活状态（状态模式），当前工具是会话状态的一部分
- 测距、测面、绘制的逻辑只接收统一的指针事件（经纬度和屏幕坐标），由当前激活的框架提供；结果写进样式模型，另一个框架通过镜像自动显示。三维测量不再需要叠一层透明的二维画布
- 点选通过查询接口完成，两个框架各有实现。二维：用渲染结果判断命中，再按几何查后端（与旧项目相同）。三维：先沿用旧做法（对齐二维后查询），以后改用瓦片数据服务（ADR 0021），不再依赖二维

### 7. 暂时沿用的旧做法

三维期间二维地图继续存活：点选沿用旧做法时需要它，切回二维也是即时的。代价见下文，做三维时再评估。

## 后果

- 好处：功能只写一次，切换框架时共享状态和独有状态都能保留；旧项目的几处补丁（标注压制、测量叠层、`styledata` 风暴、手写求值器）在这个结构里都有了正常位置
- 好处：Manager 的测试断言会话状态即可，不需要 WebGL，也不需要假引擎
- 代价：样式模型和 MapLibre 内部各有一份样式，必须遵守"只有适配器写地图"。写第一个适配器时，用 lint 限制 maplibre-gl 只能在适配器和 app 的装配中导入（ADR 0018 的待办）；逃生口只用于读
- 代价：会话状态和事件要先设计好，前期工作比沿用旧结构多
- 代价：三维期间二维继续存活，同时占着两个 WebGL 上下文和两份瓦片数据
