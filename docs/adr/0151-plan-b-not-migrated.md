# 0151. Cesium 下的资源图层（方案 B）不迁移，三维引擎仍按部署选择

- 状态：已接受（2026-11-11 用户确认；第 3 条三维引擎按部署选择由 0153 取代，Cesium 引擎已移除；第 5 条的开关由 0153 删掉，app 直接注入收窄后的能力；收窄由 0157 取消，能力原样注入）
- 日期：2026-11-11
- 修改：
  - ADR 0147 第 6 节第 3 条、第 8 节"之后"一行：方案 B 不迁移；
  - 结束 ADR 0147 的待定项"方案 B 的迁移"和 ADR 0150 后果里的"Cesium 下的资源图层（方案 B）"。

## 背景

ADR 0147 把"迁移旧项目的 Worker 栅格化（方案 B），让 `cesium` 下也显示资源图层"排在改默认引擎的门槛之后，要求单独写一份 ADR。门槛已过，默认引擎是 `maplibre`（ADR 0150）。

2026-11-10 到 11 日做了方案 B 的验证。

**证据的位置：**

- 代码：分支 `poc/cesium-mvt-raster`，标签 `poc-plan-b-2026-11`（提交 `e5f529c6`）。`packages/map-cesium/src/mvt/`（10 个文件，约 2360 行）、开发页 `/dev/plan-b`、`measure:3d` 的资源图层场景（`--only res-`）。
- 完整记录和显卡机器的原始结果不入库，在 `local/poc/plan-b/` 的 `REPORT.md` 和 `gpu-20261110-235303/`。

**做法：** 每个矢量数据源一个 Cesium 影像图层。Worker 里下载、解码、缓存几何、画到 OffscreenCanvas，位图转移回主线程。样式是应用的 `resourcesGroup`，表达式用 style-spec 求值，通信用 `@mx/utils` 的 Worker 层，解码库和 MapLibre 6.12 同版本。验证了四个资源：水域面层（重图层）、永久基本农田图斑（花纹）、行政区界线（虚线）、地类图斑（分类配色）。标注按用户的要求没有做。

**画面：** 分类配色、虚线、花纹、瓦片接缝都对，正俯视时和 MapLibre 的截图肉眼几乎分不出。固有的差别：

- 位图贴在地球上要插值，整体偏软，倾斜时远处的小图斑和细线变淡。测量工具算的清晰度，MapLibre 是方案 B 的 1.03～1.18 倍。
- 透明边缘在线性插值下发灰（没预乘的贴图），改成不插值后干净，倾斜时的副作用没有验证。
- 线宽、虚线周期、花纹疏密按整数级别烘进位图，两级之间跟着贴图缩放；透明度也烘在里面，改一下要重画。

**显卡实测：** RTX 3060 笔记本，Edge 157，1600×900，ArcGIS 影像底图，五个场景，每种引擎 3 遍取中位数，42 遍全部正常。下表每格是"方案 B / MapLibre 原生绘制"。水域面层按 9 级、基本农田按 8 级起请求，是 PoC 自己给的；应用里最小显示级别的开关现在关着（`VITE_RESOURCE_MIN_ZOOM_ENABLED=false`）。

| 场景 | 到稳定（秒） | 到稳定的瓦片请求（张，MB） | 飞行中 ≥50 毫秒的帧 | 显存稳定时（MB） |
|---|---|---|---|---|
| 水域面层 z10 | 4.9 / 4.0 | 20，57.5 / 12，21.5 | 19 / 0 | 318 / 150 |
| 四个资源 z10 | 7.4 / 3.4 | 110，86.9 / 48，30.1 | 33 / 2 | 384 / 231 |
| 四个资源 z12 倾斜 60° | 10.9 / 8.1 | 214，80.0 / 160，4.7 | 27 / 2 | 524 / 139 |
| 地类图斑加界线 z14 | 6.5 / 3.7 | 98，5.0 / 24，0.6 | 0 / 0 | 426 / 78 |
| 基本农田加水域 z12 | 5.3 / 2.7 | 53，83.3 / 24，9.3 | 11 / 1 | 391 / 104 |

- **首屏：** 到稳定方案 B 慢 1.2～2.2 倍。
- **下载：** 到稳定的字节是 MapLibre 的 2.7～17 倍。Cesium 的影像从根节点往下细分，每一级祖先都要请求，这是它的机制决定的；而这些数据粗的级别反而更重（z9 的 24 张就有 44.7 MB）。同级别的瓦片不重复下载：二维先加载过的 48 张，切到三维时全部来自浏览器缓存（`max-age=300`）。
- **飞行：** 15 秒的飞行里方案 B 有 11～33 帧超过 50 毫秒（数据轻的 z14 场景是 0），MapLibre 是 0～2 帧。每帧自己的工作量两边接近，卡的是主线程在等 GPU 进程；推测是 Worker 里的画布转位图要从 GPU 读回，没有验证。
- **显存：** 稳定时是 MapLibre 的 1.7～5.5 倍。读的是整个 GPU 进程，Cesium 的地球和底图也在里面。
- **静止帧时间：** 持平，每帧工作量 3.6～4.6 对 2.2～5.4 毫秒。
- **CPU：** 渲染进程（主线程加 Worker）到稳定用的 CPU 时间是 1.6～3.3 倍。

**做成产品还要的：**

- 静态底图改成影像：它在 Cesium 里是贴地的面实体，画在所有影像之上，实测把资源图层完全盖住。
- 每个资源都要有最小显示级别，否则祖先级别的大瓦片拖垮首屏。
- 视图契约加异步识别：点选的原型在 Worker 里 8 毫秒返回，但 `queryRendered` 是同步的；框选没有做。
- Worker 崩溃后的恢复、请求取消（Cesium 的影像请求取消不了）、三维里的选中高亮、测试。
- 估计 5000～6500 行，不含标注。之后资源图层每加一种写法，MapLibre 自动支持，方案 B 要再写一遍。

讨论时还提到过在页面上让用户切换引擎。用户的意思是保持现状："我的意思是保持现状，并没有想给用户在页面切换。那就按你的建议，先不迁，保留分支打tag。"

## 候选方案

| 问题 | 候选 | 选择与理由 |
|---|---|---|
| `cesium` 下的资源图层 | 迁移方案 B；不迁移 | **不迁移。** `maplibre` 已是默认引擎，资源图层在里面是原生绘制；方案 B 只是给可选引擎补同一项能力，实测主要几项都不如 MapLibre，还要多维护一套绘制。这项能力现在两种引擎都关着，卡在页面设计上，不是卡在引擎上 |
| PoC 的代码 | 合进 main 只给开发页用；留在分支上加标签；删掉 | **留在分支上，加标签。** 合进来的话，`packages/map-cesium` 里多出约 2300 行只有开发页用的代码，业务逻辑也成了两套。标签保证分支被删也找得回来 |
| 三维引擎怎么选 | 每个部署在构建时选（现状）；页面上给用户切换 | **保持现状。** 用户的决定。页面上切换意味着两种引擎的功能差别直接给用户看，两种都要维护到同等水平，和 ADR 0147 第 6 节相反 |

## 决定

1. **方案 B 不迁移。** `cesium` 引擎下三维不显示资源图层，三维期间点/框选不识别，维持 ADR 0078 第 1 节、ADR 0080 第 5 节；`CESIUM_ENGINE` 的能力声明不变。
2. **PoC 的代码不进 main，开发页也不进。** 留在分支 `poc/cesium-mvt-raster`，标签 `poc-plan-b-2026-11`。`measure:3d` 的资源图层场景也只在这个分支上。
3. **三维引擎仍然每个部署选一种**，构建时由 `VITE_MAP_3D_ENGINE` 决定（ADR 0147 第 1 节、ADR 0150），页面上不提供切换。ADR 0147 的待定项"是否改成部署时选择"不在这次决定里。
4. **什么时候再考虑：** 出现了必须用 Cesium 引擎、又必须在三维里看资源图层的部署。那时从标签开始，先处理背景里"做成产品还要的"几项，另写 ADR。
5. `maplibre` 下三维的资源图层不受影响：仍由 `shared/config/scene-options.ts` 的开关关着，放开前先改页面设计（ADR 0147 的状态行）。

## 后果

- **好处：** 资源图层只有 MapLibre 一套绘制。Cesium 的维护范围就是现有功能（ADR 0147 第 6 节前两条）。
- **代价：** 选 `cesium` 的部署，三维里看不到资源图层，也不能点/框选。
- **没有验证的**（重新考虑时要补）：
  - 水域面层不设最小级别时的代价（压力场景没跑）；
  - Worker 的画布加 `willReadFrequently` 能不能消掉飞行时的卡顿；
  - 半透明填充的相邻图斑之间有没有细缝；
  - 不插值采样在倾斜时会不会闪；
  - 标注。
- **已同步：** ADR 0147 的状态行、[README](README.md) 的索引、[地图架构总览](../modules/map-overview.md)里引擎和三维的两行、`docs/backlog.md`。
