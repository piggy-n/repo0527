# 0152. Cesium 下的 LCC2（方案 3：叠 Three.js 画布）不做

- 状态：已接受（2026-11-11 用户确认）
- 日期：2026-11-11
- 修改：
  - 结束 ADR 0149 候选方案"支持哪种引擎"一行里的"叠画布另做 PoC"，以及 ADR 0150 后果里待定的"叠画布的 LCC2"；
  - ADR 0147 第 6 节第 2 条不变：新的三维功能只在 `maplibre` 下做。

## 背景

ADR 0149 只在 `maplibre` 引擎下支持 LCC2。`cesium` 下要显示，只有两条路：另叠一块 Three.js 画布（两个 WebGL 上下文，深度不共用），或者用 XGRIDS 的 LCC Web SDK。SDK 的 AppKey 绑定域名，在线授权要连外网，离线授权会过期（ADR 0149），用不了。叠画布排进了三维的后续顺序（用户 2026-11-09 定），叫方案 3。

2026-11-09 做了方案 3 的验证。

**证据的位置：**

- 代码：分支 `poc/cesium-three-lcc2`，标签 `poc-plan-3-2026-11`（提交 `de17ddcf`）。它从 `poc/maplibre-three-gpu` 拉出，是 PoC 工程里的独立页面，不在应用里：`tools/poc/maplibre-three/lcc2/`（`cesium.html`、`src/cesium-page.ts`），运行和复测的说明在 `tools/poc/maplibre-three/CESIUM-OVERLAY.md`，显卡机器上复测用 `pnpm overlay`。
- 完整记录、截图和原始结果不入库，在 `local/poc/cesium-three-lcc2/` 的 `REPORT.md`、`result/`（软件渲染）和 `result-gpu/`（显卡机器）。

**做法：** Cesium 的画布照常画底图和倾斜模型，上面盖一块透明的 Three.js 画布，用 `gaussian-splat-lite` 1.6.1 画彭城广场的样例。页面自己写渲染循环：同一次 `requestAnimationFrame` 里 Cesium 先定下相机、画完，再把相机同步给 Three、画泼溅。Three 的画布不接收鼠标，绘图缓冲每帧照抄 Cesium 画布的尺寸。

**结果：** 开发机上用软件渲染跑了一次；RTX 3060 笔记本（1600×900，300 万个高斯，ArcGIS 影像底图）上全部 7 项又复测了一次，都正常。

- **位置一致：** 算出来的偏差 0 像素，画出来最大 0.71 像素（量法的分辨率约 0.5 像素）；转动、拉近、压低视角、改窗口大小、设备像素比 2 都一样。前提是两块画布在同一帧、用同一个相机画；Three 晚一帧时，每帧转 3° 就差 16～32 像素。
- **遮挡默认全错：** 泼溅总是盖在 Cesium 画的东西上面。Cesium 里 30 米的方块被盖得一个像素不剩；泼溅沉到地表以下 41 米，仍然盖住 37.7% 的画面（应当是 0）。标注、路线、第三人称的人物同样会被盖住。
- **读深度能修正：** Cesium 加一个后处理，把深度编码成颜色画到自己的画布上，Three 读成纹理、先写进深度缓冲，全部是公开接口。方块 98.7% 可见，沉到地下的泼溅 0%。代价是相机动的每一帧 Cesium 要画两遍。另一种做法是 Three 里再加载一份倾斜模型、只写深度，它只对这一份模型有效，方块只露出 9～17%。
- **性能：** 每帧 JS 加 GPU 的中位数，只有 Cesium 时 13.5～14.2 毫秒，叠上泼溅 15.1～18.2 毫秒：叠画布本身只多 2～4 毫秒，第二个上下文只占 14 MB 显存。打开读深度后 25.5～31.8 毫秒，Cesium 的 GPU 耗时是原来的 1.9 倍；相机动时帧间隔从约 21 毫秒变成约 40 毫秒，帧率大约减半。静止时按需渲染不重画，不花这份代价。
- **显存：** 大头是泼溅，每百万个约 190 MB。
- **第一人称和地下：** 能看、能走，位置一致。但进到 LCC2 里面时，倾斜模型的表面像盖子一样挡住视线，打开读深度后泼溅一个像素都看不到。这和引擎无关，ADR 0149 已经定了倾斜模型在 LCC2 的范围里裁掉。
- 真实的鼠标拖动、惯性、第一人称走动的手感，没有人看过。

**做成产品还要的：** 粗估 600～900 行，不含漫游。

- 画布和渲染循环接进 `map-cesium`，加泼溅层、读深度和按数据集的配准；
- 拾取：`scene.pick` 看不到泼溅，要另对泼溅做射线求交，再和 Cesium 的结果比远近；
- 截图、导出这类读画布的功能，要把两块画布合起来；
- 想省掉读深度时多画的那一遍，要用 Cesium 的私有接口取它内部的深度纹理，每次升级 Cesium 都要重查。

`maplibre` 引擎里，泼溅和倾斜模型在同一个上下文、同一个深度缓冲里，上面这些问题都没有（ADR 0149）。ADR 0151 已经定了：Cesium 保留为可选，只维护现有功能，三维引擎每个部署在构建时选一种，页面上不切换。

## 候选方案

| 问题 | 候选 | 选择与理由 |
|---|---|---|
| `cesium` 下的 LCC2 | 叠画布、读深度保证遮挡；叠画布、只在 LCC2 独占画面时用；XGRIDS 的 SDK；不做 | **不做。** `maplibre` 已是默认引擎，LCC2 在里面遮挡天然正确；在 Cesium 下做，是给可选引擎补一项新功能，和 ADR 0147 第 6 节相反。遮挡正确的做法相机动时帧率减半；独占画面的做法会盖住标注和路线。两种都要另写拾取和截图。SDK 的授权方式在内网用不了 |
| PoC 的代码 | 合进 main 只给开发页用；留在分支上加标签；删掉 | **留在分支上，加标签。** 和 ADR 0151 一样。它是 PoC 工程里的独立页面，合进来也只能给开发页用，还要多维护一套 Cesium 的渲染循环。标签保证分支被删也找得回来 |

## 决定

1. **`cesium` 引擎下不显示 LCC2。** 维持 ADR 0149（只在 `maplibre` 下支持）和 ADR 0147 第 6 节；`CESIUM_ENGINE` 的能力声明不变（`splats: false`：忽略会话里的泼溅，三维模型面板也不列出）。
2. **PoC 的代码不进 main。** 留在分支 `poc/cesium-three-lcc2`，标签 `poc-plan-3-2026-11`。
3. **三维路线上不再有待做的 PoC。** 方案 B（ADR 0151）和方案 3 都定了不做；三维引擎仍然每个部署选一种（ADR 0151 第 3 条）。
4. **什么时候再考虑：** 出现了必须用 Cesium 引擎、又必须显示 LCC2 的部署。那时从标签开始，先定是只在 LCC2 独占画面时用（便宜，不处理遮挡），还是要和 Cesium 的内容混着看（读深度，或者用私有接口取深度纹理），再处理背景里"做成产品还要的"几项，另写 ADR。

## 后果

- **好处：** LCC2 只有 `maplibre` 一套接入，Cesium 的维护范围不变。
- **代价：** 选 `cesium` 的部署看不到 LCC2。
- **没有验证的**（重新考虑时要补）：
  - 真实的鼠标拖动、惯性、第一人称走动的手感；
  - 用私有接口取 Cesium 内部的深度纹理，能省下多少；
  - 集成显卡上的帧率；
  - 钻地时半透明的地表在不在深度里；
  - Cesium 的视锥多于一个时，读到的深度对不对。
- **已同步：** ADR 0149 的状态行、[README](README.md) 的索引、[地图架构总览](../modules/map-overview.md)里三维模型与漫游的一行、`docs/backlog.md`。
