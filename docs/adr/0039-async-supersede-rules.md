# 0039. 异步操作的作废规则、相机操作对象与状态命名

- 状态：已接受
- 日期：2026-10-10
- 修正 ADR 0028 第 5 条（`view` 的含义、`whenReady` 的用途）、ADR 0038 第 1 条（`intentRevision`）和第 3 条（上下文的相机操作入口）

## 背景

5A、5B 的时序问题一个接一个：`whenReady` 没有绑定视图实例、加载期间开启的临时任务没有键盘焦点、区划边界到位时覆盖了加载期间的相机操作、`cameraIntent` 拿相机变化次数代表操作（ADR 0038）、地图刚就绪时旧定位在新定位之后执行（`f5ce757`）。每次都是修好一处，没有统一的规则：

1. "结果还算不算数"由各个拥有者自己判断，写法有三种：相机模型的 `AbortController` 链、区划定位的 `restart()`、位置点查询所在区县的递增计数。等待返回后要再确认一次，全靠写的人记得，`f5ce757` 修的就是漏了这一步
2. 拥有者能绕过相机操作：上下文的 `view` 带着 `flyTo`、`fitBounds`，区划定位要自己写"开始操作 → 加载 → 等就绪 → 再确认 → 定位"五步
3. `runCameraOperation` 等待期间视图失败就放弃。加载期间选中南京，引擎失败，用户点重试后地图恢复：区划定位已经放弃，初始适配也让给了这次选择，面板显示南京、边界高亮，相机却停在会话的初始相机上
4. `view` 不为 `null` 不代表能用：视图还没就绪时调用 `project` 会抛错，浮层和开发页里有 4 处同时判断 `viewState === 'ready' && view`
5. `runCameraOperation` 的回调抛错，视图已就绪时抛给调用方，没就绪时交给 `onError`。调用方不知道这一次是哪种情况
6. 命名混用："version" 既指样式模型的提交序号（`StyleModel.version`、`fromVersion`），又指样式规范的版本号（同一个文件里的 `version: 8`）；`intentRevision` 名字是"意图"，实际是"非同步原因的相机变化次数"，正是 ADR 0038 否定的那个概念，并且除了自己的测试没有使用方

## 候选方案

| 问题 | 候选 | 选择 |
|---|---|---|
| 统一到什么程度 | 各处照旧；统一的任务管理器（优先级、队列）；写明规则，加一个小工具 | 规则加小工具：跨拥有者的通道目前只有相机一个，任务管理器没有第二个使用方 |
| "后发作废先发"适用于哪些操作 | 所有命令；只适用于可替换的操作 | 只适用于可替换的操作：删除、保存这类服务端写操作，前端不再等待不等于后端撤销执行 |
| 同一通道"只认最新"的写法 | 递增计数；中止上一次的 `AbortController` | `AbortController`：信号能交给等待（`whenReady`、`fetch`）让它立即结束，计数只能在返回后比较 |
| 相机定位从哪里发起 | 拥有者拿到视图自己定位，约定先再确认；操作对象的 `run` 统一等待和确认，移动相机的能力只在回调里给出 | 操作对象：再确认由框架做一次 |
| 相机控制的有效期 | 回调之后仍然可用；只在这次回调期间有效 | 只在回调期间有效：调用方仍然可以把句柄存起来，之后再调用就绕过了作废；过期调用抛错 |
| 同一个操作多次 `run` | 每次都执行；只允许一次 | 只允许一次：一次操作对应一次相机移动，第二次是编程错误 |
| 等待期间视图失败 | 放弃（ADR 0038）；继续等，只在有新的操作、上下文释放时放弃 | 继续等：在新的操作出现之前，它就是用户最后一次的意图 |
| 跨失败等待的实现 | 循环调用 `whenReady()`；订阅视图状态的变化 | 订阅：失败视图的 `whenReady()` 立即以原因结束，循环会空转 |
| `view` 的含义 | 当前挂着的视图（可能还不能用）；只在就绪时有值 | 只在就绪时有值：拿到就能用，"有视图却不能调用"表达不出来 |
| `run` 的回调抛错 | 同步执行时抛给调用方，异步时交给 `onError`；都交给 `onError` | 都交给 `onError`：调用方不知道这一次是同步还是异步执行，不能依赖抛错 |
| `intentRevision` | 改名保留；删除 | 删除：三维还原视角的条件能从相机事件推出来（见第 5 条） |

## 决定

### 1. 异步的四类与六条规则

| 类型 | 例子 | 先后怎样处理 |
|---|---|---|
| 状态收敛 | 样式提交后视图追赶会话；区划高亮从拥有者的状态推导 | 目标总是最新状态，旧版本直接跳过 |
| 可替换操作 | 相机定位；查询位置点所在区县 | 只有最新一次的结果有意义：同一通道里后发的作废先发的 |
| 服务端读取 | 资源树、图层配置（5C） | TanStack Query 按 key 隔离（ADR 0017） |
| 服务端写操作 | 删除文件、保存配置 | 不适用"后发作废先发"：请求发出后后端就会执行，前端取消等待不等于撤销。按业务防重复（如表格按行 ID 记录进行中）、串行或允许并发；不随组件卸载取消（如文件删除不传 `signal`） |

1. **能写成状态收敛的，不写成操作**：收敛只看最新状态，没有"旧的覆盖新的"
2. **可替换操作在同一通道里后发覆盖先发，不同通道互不作废**：通道是"同一件事的先后请求"，例如相机、区划选择、位置点所在区县各是一个通道；选区划不会取消底图切换。服务端写操作不属于可替换操作
3. **用户操作作废之前的操作；初始化不开始操作**：初始化（如页面的初始适配）在当前操作下执行，被用户的操作作废就让步
4. **取消的是等待和写入，不是共享的下载**：多个使用方共用的加载不随某一次取消（ADR 0036）
5. **每个等待点返回后重新确认仍然有效**：等待因中止而结束，不等于返回时一定没中止。能由框架代做的由框架做（第 3 条的 `run`），其余由拥有者在 `await` 之后检查自己的信号
6. **释放优先于一切**：释放后等待中的操作以 `AbortError` 结束，不再写入（ADR 0023）

### 2. `LatestController`：同一通道只认最新的一次

`@yzt/utils` 提供：

- `next(reason?)`：中止当前的信号，返回新的
- `signal`：当前这一次的信号；创建时就有一个没中止的
- `abort(reason?)`：中止当前这一次，不开始新的
- 实现 `Disposable`，释放时中止当前这一次

相机模型的操作、区划定位的选择、位置点的区县查询都改用它。

### 3. 相机操作对象

map-core 的 `CameraModel.beginOperation()` 照旧返回信号。map-vue 的上下文把它包成操作对象：

```ts
interface CameraOperation {
  readonly signal: AbortSignal;
  /** 视图就绪时立即执行；没就绪时等到就绪再执行；被新的操作作废、上下文释放时放弃 */
  run(action: (camera: CameraControl) => void): void;
}

/** 移动相机的能力，只在 run 的回调期间有效；没传 padding 时避开登记过的悬浮元素（ADR 0029） */
interface CameraControl {
  flyTo(target: Partial<CameraState>, options?: FlyToOptions): void;
  fitBounds(bounds: ViewBounds, options?: FitBoundsOptions): void;
}
```

上下文的入口：

| 入口 | 用途 |
|---|---|
| `beginCameraOperation()` | 开始一次操作，返回操作对象。要先异步准备数据的定位在开始时调用，准备好后 `run` |
| `currentCameraOperation()` | 当前操作的对象，不开始新的操作。初始化在它下面 `run`，被作废就让步 |
| `runCameraOperation(action)` | 等于 `beginCameraOperation().run(action)` |

`run` 的语义：

- 每个操作最多 `run` 一次，第二次调用抛错。`currentCameraOperation()` 对同一个操作返回同一个对象，两个初始化不能认领同一个操作
- 回调最多执行一次：执行之后视图再失败、恢复，都不会重放
- 信号已中止时什么也不做
- 当前视图是 `ready` 时同步执行
- 否则等到有视图进入 `ready`：期间视图失败、重试、被替换都继续等；暂停的视图不算就绪。等到之后再确认信号没中止才执行
- 等待订阅视图状态的变化（包括视图的挂上、卸下），不循环调用 `whenReady()`；执行、操作作废、上下文释放时移除监听
- 回调抛错交给 `onError`

相机控制的有效期：

- 回调同步执行，`camera` 只在这次回调期间有效
- 方法每次执行都检查：回调还没返回、操作没被作废、视图仍是开始执行时那个就绪的视图
- 回调返回之后再调用抛错：把句柄存起来延迟调用是编程错误，类型和 lint 拦不住，要在运行时暴露，不能悄悄定位
- 回调期间操作被作废（回调里又开始了新的操作）或视图不再就绪时，什么也不做

使用方：

- 区划定位：选择时开始操作；边界到位后先确认自己的选择没过期，写入高亮，再 `run` 定位
- 默认视角：初始适配在 setup 时写成 `currentCameraOperation().run(...)`（不带动画），首次失败、重试成功后照样执行（ADR 0033）；"回到默认视角"用 `runCameraOperation`
- 坐标定位：`runCameraOperation`，不变

### 4. `view` 只在就绪时有值

上下文的 `view` 只在视图为 `ready` 时有值，内容只有 `kind`、`pick`、`project`（`MapViewport`），不再有 `flyTo`、`fitBounds`。浮层只判断 `view` 是否为 `null`。

`whenReady(signal?)` 保留，用于等待一轮加载完成，不再用于定位。

### 5. 状态的命名

| 词 | 含义 | 用在 |
|---|---|---|
| revision | 状态快照的序号，只增不减，用来比较新旧 | 样式模型的提交（`StyleModel.revision`、`StyleChange.fromRevision` / `toRevision`）、`projectionRevision` |
| operation | 一次意图的身份，只能被作废，不比较大小；用信号表示，不用编号 | 相机操作 |
| version | 只用于外部格式 | 样式规范的 `version: 8`、依赖版本 |

删除 `CameraModel.intentRevision`。ADR 0020 第 5 条、ADR 0024 的还原规则（切走期间二维只有 `sync` 的变化时，切回三维还原离开时的精确视角）保留：三维视图在隐藏期间订阅相机事件、看 `cause` 就能判断，由三维阶段实现。能从事件推出来的，不在模型里另存一份。

## 后果

- 好处：相机定位的等待和再确认由 `run` 统一完成，拥有者不再手写；移动相机的能力只在回调期间有效，存下句柄延迟调用会抛错，而不是悄悄覆盖新的定位
- 限制：这一保证在运行时成立，不在编译时。类型和 lint 拦不住把句柄存起来，误用要靠测试走到那条路径才会暴露
- 好处：加载期间选中区划、引擎失败后重试，地图恢复时定位到选中的区划；初始适配不再需要自己侦听视图状态
- 好处：浮层不再组合判断视图状态；同一通道只有一种写法；"revision"和"version"各有一个意思
- 代价：上下文的接口变了，区划定位、默认视角、坐标定位、两个浮层、地图开发页和相关测试都要改
- 代价：等待的操作可能在很久之后（重试成功时）执行。这是有意的：在新的操作出现之前，它就是用户最后一次的意图
- 代价：相机以外的可替换操作（如区县查询）仍要拥有者在 `await` 之后检查自己的信号，第 5 条规则只对相机做到了框架代做
- 三维阶段：三维视图按 ADR 0038 第 2 条报告手势开始的操作，还原精确视角的判断按第 5 条在三维视图里实现
