# 0005. 依赖维护与持续集成

- 状态：已接受
- 日期：2026-09-29

## 背景

旧项目的 Vite 锁死在 4.4.11，依赖分类混乱，ESLint 靠关掉规则才能通过，说明依赖维护和质量门禁一直没有形成流程。
新项目希望建立一套稳定的依赖维护和发布流程，同时控制前期成本。
需要决定三件事：CI、依赖更新自动化、版本发布分别从什么时候开始；依赖更新遵守什么规则；多久执行一次。

## 候选方案

开始时机：

1. 等基础结构和核心功能稳定后，一次性建立 CI、依赖自动化和发布流程
2. 按先后依赖分阶段：CI 最先；依赖自动化等有测试之后；发布流程等首次部署之前

更新频率：

1. 每周手动检查
2. 每月手动检查
3. 由自动化工具每周处理小版本和补丁，大版本每月集中评审

## 决定

开始时机选方案 2：

- 阶段 1 接入最小 CI（GitHub Actions）：`pnpm install --frozen-lockfile` → 类型检查 → lint → 测试 → 构建
- 阶段 3 之后，测试覆盖到真实业务时，再接入 Renovate
- 版本号格式、CHANGELOG 与发布工具、CD，在首次部署前另写 ADR 决定；在此之前保持 Conventional Commits 提交格式

更新规则：

- 一般依赖使用 `^` 范围；不遵守语义化版本的包精确锁定，目前有 Cesium、TypeScript
- 0.x 版本的包，小版本升级按大版本对待
- 配置 pnpm 的 `minimumReleaseAge`，新版本发布满一定时长后才允许安装，至少 1 天，具体值在阶段 1 确定
- 小版本和补丁：CI 通过后合并
- 大版本（以及上面按大版本对待的情况）：
  - 先读 Breaking Changes 和迁移指南，评估成本后再决定是否升级
  - 不追 x.0.0，等出过几个补丁版本再升
  - 一次只升一个包，单独提交，提交说明里写明做了哪些迁移
- 安全告警不等周期，随时处理；开启 GitHub Dependabot 的安全告警，不启用它的版本更新
- `pnpm-lock.yaml` 必须提交

更新频率：

- 接入 Renovate 之前：每月手动检查一次（`pnpm deps:check`）
- 接入之后：Renovate 每周把小版本和补丁合成一个 PR，CI 通过后自动合并；大版本每个单独开 PR，每月集中评审一次

阶段 1 要落地的事项：

- 最小 CI 工作流
- 在 `pnpm-workspace.yaml` 中配置 `minimumReleaseAge`
- 根 `package.json` 中的 `typescript` 从 `^7.0.2` 改为精确版本
- `deps:update:allow-major` 改为交互式的 `pnpm update -r -i --latest`
- 开启 Dependabot 安全告警（需要在 GitHub 仓库设置中手动操作）

## 后果

- 好处：质量门禁从第一天起保持通过，不会再出现靠关掉规则让检查通过的情况
- 好处：每次更新的改动都很小，出了问题容易定位和回退
- 好处：冷却期降低了装到恶意版本的风险
- 代价：安全补丁也要等冷却期结束才能装，紧急时需要对单个包手动豁免
- 代价：自动合并完全依赖测试质量，测试覆盖不到的视觉和交互问题仍要人工检查
- 代价：精确锁定的包不会自动获得补丁，需要定期主动评估升级
